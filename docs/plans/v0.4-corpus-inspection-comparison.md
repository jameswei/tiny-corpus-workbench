# Milestone v0.4 — Corpus Inspection and Comparison

**Status:** Accepted by the project owner on 2026-07-25.

## Summary and Planning Handoff

Build one local, offline corpus command that processes an explicit small corpus
through the released observation and diagnosis contracts, aggregates evidence
across documents, and publishes a static navigable report. It may compare
explicitly listed existing revisions, but it must never draft, approve, reject,
or apply refinements.

The implementation begins from clean `main` at `4e7e6a0` on
`milestone/v0.4-corpus-inspection-comparison`. This accepted plan and the
corresponding `CURRENT.md` activation are the planning-only first commit. That
commit contains no product-code, roadmap, proposal, website, or learning
changes.

Use two committed example corpora:

- A 12-member golden matrix covering three document families in PDF, DOCX,
  Markdown, and text.
- A separate five-member quality corpus containing the existing diagnosis and
  refinement sources. It demonstrates D002, D003, D004, D005, D007, D009, and
  D010 without conflating those cases with the golden families.

## Public Interfaces and Contracts

Add:

```text
tcw inspect-corpus CORPUS_SPEC
  [--output-root build/corpus-inspection]
  [--docling-artifacts .cache/docling/models]

tcw verify-corpus CORPUS_DIRECTORY
  [--spec CORPUS_SPEC]
```

`inspect-corpus` prints one compact sorted JSON line with `corpus_id`,
`snapshot_id`, `run_id`, `member_count`, `status`, and the absolute manifest
path. It writes diagnostics only to stderr.

`verify-corpus` prints one compact JSON verification result. It never repairs
or regenerates a corpus run.

Add four closed Draft 2020-12 schemas:

- `tcw.corpus-spec/v0.4`
- `tcw.corpus-manifest/v0.4`
- `tcw.corpus-summary/v0.4`
- `tcw.corpus-verification-result/v0.4`

A corpus specification contains:

```text
schema_version
corpus_id
title
members[]
  member_id
  family
  format                  # pdf | docx | md | txt
  source                  # local path
  revisions[]             # optional
    refinement
    diagnosis
    base
```

Contract rules:

- Resolve input paths relative to the corpus-specification directory.
- Accept only explicit local paths. Do not support URLs, stdin, directory
  discovery, or globs.
- Require unique member IDs and resolved source files.
- Validate the declared format against the source suffix and media type.
- Reject symlinked specifications, sources, artifact directories, and unsafe
  filesystem nodes.
- A revision entry must identify an existing `APPLIED` v0.3 refinement plus the
  exact diagnosis and base needed for full verification.
- Require revision artifact integrity `VERIFIED`; diagnosis and base states
  `MATCH`; and derivation and reversibility states `MATCH`.
- Require each revision's source hash and media type to match its corpus
  member.
- Do not accept rejected refinement records as revisions because they contain
  no prepared document.
- Do not add a public Python API, service, database, or configuration
  framework.

The logical `corpus_id` comes from the specification. A deterministic
`snapshot_id` binds the normalized specification, captured source identities
and hashes, extractor/ruleset/runtime configuration, model inventory when
required, and verified revision identities.

## Execution, Publication, and Report Behavior

### Corpus execution

- Validate the complete specification and locked runtime before processing
  members.
- Process members sequentially in stable `member_id` order. Do not add
  concurrency, caching, or resume behavior in v0.4.
- Run the existing observation path for every member.
- Run diagnosis whenever the observation contains a usable canonical Docling
  document. MarkItDown remains descriptive and never creates findings.
- Continue after member-level validation, extraction, or diagnosis failures so
  the report can explain incomplete corpus coverage.
- Never call the refinement draft or resolution paths. Existing revisions are
  read-only inputs.
- Snapshot the specification, all sources, external revision bundles, and the
  shared PDF model inventory before processing. Recheck them immediately
  before publication.
- Abort the complete corpus publication with exit `5` if any snapshotted input
  changes during the run.

### Atomic output

Publish below:

```text
<output-root>/<corpus-id>/<corpus-run-id>/
  corpus-manifest.json
  corpus-spec.json
  summary.json
  report/
    index.html
    styles.css
  members/
    <member-id>/
      observations/<source-key>/<observation-run-id>/...
      diagnoses/<source-key>/<subject-id>/<diagnosis-run-id>/...
```

Build the complete run in a private sibling staging directory and publish it
with one exclusive atomic rename. Nested observations and diagnoses retain
their existing artifact layouts and verification contracts. Never overwrite
an earlier corpus run or publish inside an input directory.

`corpus-manifest.json` records:

- corpus, snapshot, run, runtime, and input-specification identities
- overall status and summary counts
- each member's source identity, observation and diagnosis identities,
  statuses, and relative manifest paths
- verified external revision identities and inventory fingerprints
- immutable descriptors for the normalized specification, summary, HTML, and
  CSS

`summary.json` contains deterministic, source-text-free aggregation:

- totals by corpus/member status, family, and format
- extractor-view availability and existing comparison metrics
- exact Docling-versus-MarkItDown deltas per member
- findings grouped by rule, severity, family, and format
- affected-member counts without copying arbitrary source passages
- revisions grouped by family, format, finding rule, and refiner
- revision ID, parent identity, chain length, affected-reference count, and
  before/after document hashes
- member-level errors using stable sanitized codes and messages

Do not add quality scores, semantic-equivalence claims, extractor rankings,
automatic recommendations, or aggregate severity scores.

### Static HTML

Generate an offline report with no JavaScript, remote resources, analytics,
fonts, or network calls. Use standard-library HTML escaping and local CSS; add
no rendering dependency.

The report contains:

- overview and completion status
- family × format corpus matrix
- per-extractor comparison tables
- findings by rule and severity
- revision and transformation-history comparisons
- incomplete-member and integrity sections
- anchor navigation and relative, URL-encoded links to local observation,
  comparison, diagnosis, finding, refinement, decision, history, and
  prepared-document artifacts

Do not embed arbitrary source passages or prepared-document text. The report
links to evidence instead.

Generated observations and diagnoses use self-contained relative links.
Optional revision links point to the explicitly supplied local records; moving
those external records may break the links and is documented as a local-path
limitation.

### Status and exits

Overall status:

- `COMPLETE`: every member has both extraction views, a usable canonical
  document, a completed diagnosis, and every listed revision fully verifies.
- `PARTIAL`: at least one member has usable reportable evidence, but another
  extractor, diagnosis, member, or revision is incomplete.
- `FAILED`: no member produced a usable extraction view.

Exit codes:

| Exit | Meaning |
|---|---|
| `0` | Complete corpus report published or corpus integrity verified |
| `1` | Unexpected internal failure |
| `2` | Invalid command, corpus specification, or corpus-directory argument |
| `3` | Partial corpus report published |
| `4` | Failed corpus report published with no usable member view |
| `5` | Input mutation, corpus integrity failure, unsafe path, or publication conflict |
| `6` | Incompatible CPython, lockfile, schema runtime, or global dependency contract |

A missing PDF model is recorded as a PDF-member failure. Non-PDF members
continue. A global runtime mismatch prevents publication and exits `6`.

### Corpus verification

Default verification is self-contained and checks:

- corpus schemas, canonical JSON, identities, hashes, statuses, summaries, and
  exact inventory
- every nested observation through the released observation verifier
- every nested diagnosis against its nested observation, including a fresh
  deterministic rule evaluation
- exact regeneration of `summary.json`, `report/index.html`, and
  `report/styles.css`
- safe relative report links and expected artifact roles

With `--spec`, additionally compare the original specification, current source
identities, model inventory where applicable, and external revision bundles.
Report these as advisory input states (`MATCH`, `CHANGED`, `MISSING`, or
`ERROR`) separate from historical corpus artifact integrity. Advisory drift
does not change exit `0` for an internally intact corpus, matching the existing
verifier model.

## Runtime Compatibility and Implementation Structure

Set the package version to `0.4.0`. Keep every third-party dependency pin
unchanged and use only the standard library for corpus aggregation and HTML
generation. The project entry in `uv.lock` and the exact lockfile hash will
change.

Before corpus implementation, run a mandatory compatibility spike:

1. Generate representative v0.3 diagnosis, applied revision, rejected record,
   and chained revision artifacts with the released v0.3 runtime.
2. Install the v0.4 package metadata and updated lockfile.
3. Verify all historical v0.3 artifacts and rerun diagnosis over an old applied
   revision.
4. Create and verify a new successor refinement under v0.4.
5. Reverify representative v0.2 diagnoses and all v0.1 observations.

Preserve v0.3 artifact schema versions for unchanged diagnosis and refinement
behavior. Persist the actual v0.4 package and lock identity in newly created
v0.3-format artifacts.

Update v0.3 runtime validation to accept exactly:

- the historical v0.3 package/lock pair; or
- the active v0.4 package/lock pair

Both pairs must retain CPython 3.12 and the exact existing third-party
dependency mapping. Reject mixed pairs and arbitrary package or lock values. Do
not rewrite historical artifacts or weaken dependency verification.

Stop and return to the owner if this spike cannot preserve backward
verification without changing dependency pins, artifact meaning, refinement
behavior, or the trusted-local boundary.

Implement corpus behavior in a separate lazily loaded module rather than
expanding the already large v0.3 module. Keep `cli.py` limited to argument
definition, lazy dispatch, compact output, and exit translation.

## Fixtures, Tests, and Acceptance

Add the two corpus specifications under a versioned fixture directory. Do not
add new raw documents.

A deterministic specification checker must prove:

- the golden specification contains exactly the 12 registered fixtures
- it contains exactly three families and four formats per family
- the quality specification contains exactly the five existing
  diagnosis/refinement sources
- paths, membership, family/format metadata, and expected rule coverage match
  the existing registries
- repeated checks do not rewrite fixtures

Required unit and contract coverage:

- closed-schema validation and canonical serialization
- duplicate IDs/sources, unsupported formats, unsafe paths, symlinks, missing
  sources, and malformed revision bundles
- stable snapshot identity and ordering
- aggregation by family, format, extractor, rule, severity, and refiner
- HTML escaping, offline assets, navigation, and link safety
- absence of source text, scripts, remote resources, rankings, and semantic
  claims
- complete, partial, and failed status/exit behavior
- MarkItDown-only, Docling-only, model-missing, diagnosis-failure, and
  revision-verification cases
- atomic publication, no-overwrite behavior, concurrent publication, staging
  cleanup, input mutation, and exact inventory rejection
- corruption of every top-level report artifact and nested record type
- default verification and all optional live-input advisory states
- backward verification of v0.1, v0.2, and v0.3 artifacts under package v0.4

Required integration scenarios:

1. Run the full golden matrix offline with prefetched PDF models. Require 12
   members, three families, four formats, both extractor views, completed
   diagnoses, and the documented clean-finding outcome.
2. Run the five-member quality corpus. Require the exact expected coverage of
   D002, D003, D004, D005, D007, D009, and D010.
3. Create one explicit D009 revision through the released human-decision
   workflow, add its verified revision bundle to a temporary quality
   specification, and require revision comparison in JSON and HTML.
4. Create a two-step revision chain and verify chain length, parent links,
   refiners, hashes, and report links.
5. Remove PDF models and require a partial report for the remaining formats
   without network access.
6. Verify deterministic summary/report rendering from the same captured
   evidence.
7. Run all documented commands from a clean checkout using CPython 3.12.

Extend fast CI with schemas, unit tests, corpus-specification checks, HTML
validation, compilation, fixture checks, portability, and diff hygiene. Extend
full CI with the two offline corpus runs and revision-comparison integration.

## Assumptions and Exclusions

- The recommended safe-pipeline and two-example-corpus choices are accepted as
  defaults because no alternative preference was supplied.
- Corpus inspection is sequential, local, offline, and intended for small
  explicit corpora.
- Existing revisions are compared read-only and require complete v0.3
  verification inputs.
- Original sources, observations, diagnoses, refinements, and prepared
  revisions remain unchanged.
- No batch approval, batch refinement, semantic rewriting, OCR expansion,
  directory crawling, connectors, background service, HTTP API, interactive
  UI, public Python API, JavaScript report application, database, RAG
  processing, or production orchestration is included.
- v0.5 remains inactive after v0.4 release.
