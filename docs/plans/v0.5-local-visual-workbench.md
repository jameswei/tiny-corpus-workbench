# v0.5 — Local Visual Workbench

## Outcome

v0.5 established the final learning-first record model and added a bundled
read-only Local Visual Workbench. The browser helps learners inspect explicit
verified records while the `corpus` CLI remains the only lifecycle execution
and mutation surface.

The milestone retained four persisted record families:

- observations own source identity, extractor evidence, canonical content, and
  descriptive comparison;
- diagnoses own deterministic findings without mutation authority;
- refinements own one explicit human decision and any immutable successor;
- corpora own aggregate, source-text-free inspection of explicit members.

Each family keeps its own self-contained persisted schema responsibilities.
Transient verification results use dependency-free frozen Python values. They
do not have persisted verification-result schemas.

## Final design rationale

The design keeps the learning sequence visible: preserve evidence, diagnose,
decide, and only then create a new revision. Original sources and raw
extraction artifacts remain immutable. Diagnosis does not authorize mutation.
Interpretive refinement remains under explicit human control.

Drafting produces only the canonical proposal. The
`refinement-manifest.json.decision` field is the only persisted structured
decision authority. Proposal state and transformation state describe lifecycle
facts; they do not duplicate approval authority.

Framework-neutral application services compose the same domain data for the
CLI and Workbench. The browser receives lightweight internal payloads rather
than persisted schemas. This keeps storage contracts, transient verification
values, and presentation data separate.

## Workbench boundary

The bundled Workbench is a foreground, single-user learning tool. It binds only
to `127.0.0.1`, serves captured bytes and an immutable in-memory projection,
and renders record details without changing them.

Its HTTP routes are a lightweight internal bridge for the bundled HTML, CSS,
and JavaScript. They are not a public or stable API. The Workbench does not
upload files, execute workflows, persist sessions, expose remote binding, or
replace the CLI.

The trusted-local model detects ordinary record corruption with hashes and
verification. It does not claim authorship, authenticity, a trusted timestamp,
or protection from hostile local processes. Distribution remains source-only.

## Fixtures and validation outcome

The final fixture roles are distinct:

- golden fixtures teach supported formats and stable extraction anchors;
- diagnosis fixtures exercise deterministic finding rules;
- refinement fixtures exercise rejection, approval, lineage, and reversal;
- corpus fixtures exercise aggregate comparison and incomplete members;
- test-only fixtures cover focused failure and boundary cases.

Validation covered persisted record verification, corpus tamper detection,
atomic publication, source immutability, explicit refinement approval,
producer-consumer payload coverage, safe text rendering, loopback-only serving,
fixture integrity, site assets, portability, and focused Fast and Full CI
responsibilities. Documentation policy is not an executable product check.

## Boundaries and later direction

v0.5 did not add a hosted service, public API, browser-side workflow execution,
authentication, multi-user state, remote resources, production orchestration,
or downstream RAG work.

v0.6 added fixed-layout workspace discovery and transactional refresh. Current
Workbench behavior belongs to the
[Local Visual Workbench guide](../local-visual-workbench.md).
