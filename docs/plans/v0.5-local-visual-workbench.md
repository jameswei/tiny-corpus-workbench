## Outcome

Deliver a local, loopback-only visual workbench over explicitly supplied current observation, diagnosis, refinement, and corpus records.

The browser must inspect:

- captured source identity and provenance;
- Docling and MarkItDown observation/comparison evidence;
- diagnosis rules, findings, evidence, and affected references;
- approved and rejected decisions;
- transformations, lineage, hashes, and revision chains;
- corpus family × format matrices and aggregates;
- artifact integrity separately from cross-record relationship completeness;
- valid but partial, failed, rejected, or otherwise incomplete records.

The workbench is read-only. Existing CLI commands remain the only execution and mutation surface.

## Boundaries and exclusions

The milestone remains within raw document → extraction → canonical representation → diagnosis → controlled prepared revision.

It does not add:

- observation, diagnosis, drafting, approval, rejection, resolution, repair, publication, or evidence rewriting through HTTP/UI;
- directory discovery, recursive record search, neighbor discovery, globs, stdin, URLs, registries, or configuration frameworks;
- source-path following, source-file serving, arbitrary report-link traversal, or external revision-path traversal;
- persistence, cache, resume, filesystem watching, background jobs, databases, or concurrency machinery;
- configurable non-loopback hosting, hosted services, authentication systems, or a public Python API;
- frontend build tooling, frontend/runtime dependencies, remote assets, analytics, fonts, or network calls beyond the bound loopback origin;
- chunking, embeddings, indexing, retrieval, reranking, generation, RAG evaluation, or downstream integration.

Sources and raw extraction artifacts remain immutable. Diagnosis grants no mutation authority. Interpretive refinements still require explicit human confirmation. Trusted-local hashes remain tamper evidence, not authorship or authenticity proof.

Lookup is by `provenance_id` only; readers do not search the registry by a normalized field tuple:

1. Load and validate the registry, including unique IDs/tuples and canonical ordering.
2. Resolve the recorded `provenance_id` to exactly one entry.
3. Compare every shared recorded field to that entry.
4. Compare each artifact-specific `extractor_contract`, `command_id`, or `generator_id` field to the same entry and its allowed identifier list.

Because a valid registry is unique and lookup is by ID, a well-formed artifact can never produce multiple matches.

Within the v0.5 baseline the registry is monotonic:

- A non-breaking package release appends its truthful tuple before it writes artifacts.
- It does not delete or mutate an earlier v0.5 entry.
- It adds committed representative artifacts for the new tuple.
- Current readers/verifiers test every registry entry for schema, intrinsic integrity, and applicable workflow verification.
- The active runtime tuple must match exactly one registry entry and list the active command or generator identifier.
- A tuple that changes artifact meaning or cannot remain readable requires a new schema baseline, not deletion of an entry.

Validation precedence for CLI commands is:

1. Validate the active installed runtime against source metadata and the registry.
2. Validate input schema version and structure.
3. Resolve recorded `provenance_id` and compare every required applicable field to its one registry entry.
4. Continue artifact verification.

## CLI and startup contract

Add exactly:

```text
tcw workbench RECORD [RECORD ...]
  [--port PORT]
  [--no-open]
```

`RECORD` is an explicit observation, diagnosis, refinement, or corpus root directory, never a manifest path.

- Default port: `8765`
- Valid range: `1024`–`65535`
- Fixed host: `127.0.0.1`
- No host option and no non-loopback mode
- Foreground standard-library server only

After successful bind, admission, corpus expansion, and projection construction, stdout emits and flushes one canonical compact JSON line:

```json
{"api_url":"http://127.0.0.1:8765/api/v0.5/workbench","contained_record_count":2,"record_count":4,"runtime":{"package_version":"0.5.0","provenance_id":"bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb"},"schema_version":"tcw.workbench-startup/v0.5","session_id":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","status":"READY","top_level_record_count":2,"url":"http://127.0.0.1:8765/"}
```

The package value and provenance ID are representative, not schema constants. In real output they come from the same validated active registry entry. This startup example and the inline closed error example below are parsed as canonical JSON and validated against their exact schemas; committed startup/projection/detail/error examples receive the same validation.

Diagnostics use stderr only. Unless `--no-open` is present, the command attempts to open the loopback URL after readiness; browser-open failure is a sanitized non-fatal warning. Ctrl-C closes the socket, emits no traceback, and exits `0`.

Existing command names, arguments, compact stdout JSON, stderr separation, and exits `0`–`6` remain where compatible with the v0.5-only reset.

## Intrinsic admission

Admission is all-or-nothing and first evaluates each supplied root independently.

Known root manifests are:

| Kind | Root manifest |
|---|---|
| Observation | `manifest.json` |
| Diagnosis | `diagnosis-manifest.json` |
| Refinement | `refinement-manifest.json` |
| Corpus | `corpus-manifest.json` |

Every supplied root must have intrinsic artifact integrity `VERIFIED`, including:

- exactly the known root-manifest kind and v0.5 schema;
- a safe existing non-symlink root directory;
- safe regular non-symlink files and safe non-symlink directories for every accessed node;
- canonical JSON and closed-schema validity;
- internal inventory, sizes, hashes, statuses, run identity, and evidence identity;
- root-name/run-ID and internal manifest/artifact consistency;
- applicable self-contained transformation/history consistency that does not require an absent external record;
- stable filesystem evidence during admission.

Intrinsic admission does not require a diagnosis subject, refinement diagnosis, refinement base, or external corpus refinement root to be supplied. Missing cross-record inputs do not fail intrinsic admission and are never opened or replayed implicitly.

Reject:

- unknown or old schemas;
- manifest files instead of root directories;
- symlinked roots or accessed nodes;
- traversal, aliases, unsafe node types, or escaping paths;
- repeated explicit roots;
- two explicitly supplied roots representing the same logical record;
- intrinsic schema, inventory, identity, size, hash, or status failure;
- input mutation during admission.

### Required v0.5 relationship references

v0.5 manifests add explicit target references so relationship resolution is singular and does not infer from paths:

- A diagnosis manifest records `subject.kind`, `subject.identity_type`, `subject.identity_value`, `subject.run_id`, `subject.manifest_sha256`, and `subject.canonical_document_sha256`.
- A refinement manifest records a `diagnosis` reference containing diagnosis ID, run ID, diagnosis-manifest SHA-256, and findings-artifact SHA-256.
- A refinement manifest records a `base` reference containing base kind, identity type/value, run ID, base-manifest SHA-256, and canonical-document SHA-256.
- An applied refinement whose base is a refinement also records a `parent` reference containing revision ID, run ID, refinement-manifest SHA-256, and prepared-document SHA-256. The field is null for an observation base and for a rejected record.
- Each corpus member has the closed observation/diagnosis stage records and status tuples defined below. A non-null nested-manifest descriptor is the only authority to expand that record.
- Each corpus external-revision summary records revision ID, refinement run ID, refinement-manifest SHA-256, and prepared-document SHA-256.

All relationship-reference objects are closed. Required hashes cannot be omitted. Relationship nullability is limited to the status tuples below and the expected-target content hash derived from an allowed null corpus-observation canonical-document hash.

### Corpus member stage records

Each corpus manifest member contains closed `observation` and `diagnosis` objects. Their nested `manifest` value is either null or the closed corpus-relative descriptor `{path, size, sha256}`: `path` is a normalized safe relative path, `size` is a positive integer, and `sha256` is lowercase hexadecimal. ### Candidate-resolution algorithm

For each physical record, complete intrinsic verification first. Then:

1. Compute its pre-record-key `logical_copy_key` from kind, v0.5 record schema, complete kind identity, and run ID.
2. Group physical copies by `logical_copy_key`.
3. Compare every copy in a group byte-for-byte and descriptor-for-descriptor under the equivalence rules below. Any difference rejects before `record_key` computation.
4. Deduplicate an equivalent group, choose canonical backing, and compute its `record_key`.
5. For each relationship, find identity candidates by target kind, record schema, identity type/value, and recorded run ID.
6. Zero identity candidates yields `MISSING`, except mandatory corpus containment, which rejects.
7. One identity candidate must match every non-null recorded manifest/content hash and pass the relation-specific evaluation. Otherwise reject.
8. More than one logical candidate for the complete kind/schema/identity/run tuple rejects as ambiguous. Equivalent physical copies have already collapsed to one logical candidate.

A present record with the same kind/identity but a different recorded run ID is a different logical record and does not satisfy the relationship. If no exact-run candidate exists, the edge is `MISSING`; if an exact-run candidate exists but its required manifest/content hash differs, admission rejects rather than reporting `MISSING`.

An applied refinement’s forward/reverse evaluation runs only when its exact diagnosis and base candidates are both present. If either is absent, applicable derivation and reversibility are `NOT_CHECKED`. A rejected refinement never runs them and reports `NOT_APPLICABLE`.

No admitted projection contains `MISMATCH`; mismatch, ambiguity, or failed required evaluation rejects admission.

## Deterministic corpus expansion

A supplied corpus root expands only the non-null nested observation and diagnosis manifest descriptors recorded in its already verified corpus manifest.

1. Iterate corpus members in stable `member_id` order.
2. Apply the complete stage-status tuple constraints; skip null descriptors without probing any path.
3. Follow only each non-null recorded relative nested observation/diagnosis manifest descriptor.
4. Recheck containment, node type, symlink rejection, recorded size/hash, v0.5 schema, supported provenance, status/identity/run/content binding, and intrinsic integrity.
5. Project each verified nested record as a child logical node, including an intrinsically valid `FAILED` observation.
6. Deduplicate it against other contained copies and any explicit top-level root.
7. Add the applicable containment edge with `MATCH`; no descriptor means no node and no edge.

A verified corpus nested descriptor that is missing, unsafe, changed, or intrinsically invalid fails corpus admission. It is not an optional missing relationship.

Corpus expansion never follows:

- recorded source paths;
- sibling directories;
- recursive record searches;
- report HTML/CSS links;
- arbitrary relative links;
- external refinement paths.

External revision summaries remain structured corpus-detail entries. An external refinement becomes a full logical node and `MATCH` target only when that refinement root is supplied explicitly. Otherwise the corpus emits a `CORPUS_EXTERNAL_REFINEMENT` edge with `MISSING` and never opens the recorded external path.

Only expanded records count as contained logical nodes. Null `FAILED`/`NOT_RUN` stage records affect corpus member status/aggregates but do not increment startup/projection record counts, appear in `contained_record_keys`, contribute a contained record key to `session_id`, authorize artifacts, or emit edges. Contained nodes count toward the session and authorize only their root manifest plus their own manifest-listed supported JSON/Markdown artifacts.

## Canonical JSON and derived identities

For all identity preimages, canonical JSON is exactly:

It is compact sorted-key UTF-8 JSON with no terminal newline. Tests compare exact preimage bytes and resulting SHA-256 values.

## Logical deduplication and canonical physical backing

Deduplication produces one logical node and one `record_key`, but every encountered physical copy must independently pass intrinsic verification. Copies are grouped by `logical_copy_key` before `record_key` exists; the common verified manifest SHA-256 is added only after equivalence succeeds.

Equivalent copies must have identical:

- kind and v0.5 record schema;
- complete kind identity and run ID;
- root-manifest bytes, size, and SHA-256;
- intrinsic status and record identity;
- the complete authorized descriptor union `U(record)`, including root/listed origin, roles, relative paths, recorded media types, sizes, SHA-256 values, and derived availability.

Before `record_key` exists, comparison uses canonical manifest bytes first, then the union’s sorted descriptor preimages `(origin, role, relative_path, recorded_media_type, size, sha256, availability)`, then status/identity fields. Any difference rejects the complete session as an identity conflict. An equivalent group has one common manifest SHA-256 and therefore one common `record_key`; only then are artifact keys computed, checked for uniqueness, and used for API ordering.

Repeated explicit roots or multiple explicitly supplied roots for the same logical record are duplicate-input errors. Therefore at most one explicit top-level backing exists.

Choose the authorized physical backing:

1. If an explicit top-level root exists, it is canonical.
2. Otherwise choose the contained copy with the lexicographically smallest:

```text
(containing_corpus_record_key, member_id, descriptor_relative_path)
```

Only canonical backing:

- supplies the exact authorized descriptor union `U(record)`;
- can be read by artifact GET;
- is rechecked after admission.

Noncanonical copies remain relationship provenance only. They receive no independent artifact keys and are never served. Their later mutation does not alter the frozen projection or trigger `409`; restart re-admits them and may reject. Canonical backing mutation or disappearance causes affected artifact GET to return `409`.

Containment edges and corpus matrix entries preserve corpus/member provenance. Record-detail responses expose no supplied root, backing path, inode, device identity, or backing-selection tuple.

- D004: `count >=2` equal to reference count, `normalized_character_count >=80`, and `normalized_text_sha256`; at least two text references.
- D005: `current_level`, `previous_level`, and optional `previous_ref`; current is more than one above previous; `document_refs` contains exactly one reference and it starts with `#/texts/`; `previous_ref` is absent exactly when previous is zero and, when present, also starts with `#/texts/`.
- D006 orphan shape has only `relationship_kind: orphan_caption` and exactly one `#/texts/` reference. Invalid-declared shape has exactly `relationship_kind: invalid_declared_caption` and string `declared_ref`; owner refs are one or two table/picture refs when the declared ref is one of them, otherwise exactly one table/picture owner; `document_refs` equals the sorted unique union of owners and the nonempty declared ref.

## HTTP server contract

Use the foreground standard-library `HTTPServer`, not a threaded/background server.

Allowed routes are exactly:

```text
GET|HEAD /
GET|HEAD /assets/workbench.css
GET|HEAD /assets/workbench.js
GET|HEAD /api/v0.5/workbench
GET|HEAD /api/v0.5/records/{record_key}
GET|HEAD /api/v0.5/artifacts/{artifact_key}
```

Record/artifact routes accept only lowercase 64-hex keys. No route accepts a filesystem path, query string, or fragment.

### Host and Origin

Validate authority for every method/path before routing, body handling, or artifact lookup.

Host:

- Require exactly one `Host`.
- Missing or duplicate Host: `400 BAD_REQUEST`.
- After normal field-name case folding and outer optional-whitespace parsing, accept only `127.0.0.1:<bound-port>`.
- Any other value: `403 HOST_REJECTED`.

Origin:

- May be absent.
- If present, require exactly one.
- Duplicate Origin: `400 BAD_REQUEST`.
- Accept only `http://127.0.0.1:<bound-port>`.
- Any other value: `403 ORIGIN_REJECTED`.

Do not accept localhost, IPv6, trailing-dot hosts, omitted/default ports, user-info, proxy-derived values, `Forwarded`, `X-Forwarded-*`, comma lists, internal whitespace variants, or value case variants.

### Total request-validation precedence

For every syntactically parseable request, apply this total order and stop at the first failure:

1. Host cardinality: missing or more than one → `400 BAD_REQUEST`.
2. Host value: anything except the exact bound authority → `403 HOST_REJECTED`.
3. Origin cardinality: absent is allowed; more than one → `400 BAD_REQUEST`.
4. Origin value: when present, anything except the exact bound origin → `403 ORIGIN_REJECTED`.
5. Request-target validation: over 8 KiB → `413 REQUEST_TOO_LARGE`; malformed form, query, fragment, control, malformed/repeated percent encoding, backslash, or dot segment → `400 BAD_REQUEST`.
6. Remaining-header validation: more than 32 fields or 32 KiB total → `413 REQUEST_TOO_LARGE`; obsolete folding, invalid field syntax, `Forwarded`, any `X-Forwarded-*`, or any `Transfer-Encoding` → `400 BAD_REQUEST`.
7. Body declaration: duplicate/malformed `Content-Length` → `400 BAD_REQUEST`; a single decimal zero is allowed; any positive length → `413 REQUEST_TOO_LARGE`.
8. Method: anything except GET/HEAD → `405 METHOD_NOT_ALLOWED`.
9. Route/key lookup: unknown route or syntactically valid unknown key → `404 NOT_FOUND`.
10. Response/artifact handling: authorization, canonical-backing recheck, response size, and handler failure produce the applicable `409`, `413`, or `500`.

Malformed HTTP framing that cannot produce a request/header multimap returns `400 BAD_REQUEST`; it cannot be combined meaningfully with later semantic conditions. The handler buffers a parseable request under a fixed transport ceiling before applying the ordered application checks above.

Combined-invalid cases follow the order without exception:

- duplicate Host beats wrong/duplicate Origin, bad target, body, method, and route;
- wrong Host beats every Origin or later failure;
- duplicate Origin beats wrong Origin and later failure;
- wrong Origin beats target/header/body/method/route failures;
- invalid target beats header/body/method/route failures;
- header failure beats body/method/route failures;
- body failure beats method/route failures;
- unsupported method beats unknown route.

Thus an invalid-authority POST receives the authority error, while the same POST with valid authority receives `405`.

### Request and response handling

- Permit only GET and HEAD.
- `HEAD` returns the same status, content type, security headers, and `Content-Length` as GET, without a body.
- Apply query, decoding, control, NUL, backslash, dot-segment, body, and transfer-encoding rejection at the exact precedence stages above.
- Request-target limit: 8 KiB.
- Header limit: 32 fields and 32 KiB total.
- Structured JSON response limit: 4 MiB.
- Explicit artifact-content limit: 16 MiB.
- Oversized authorized artifacts remain metadata-visible with `availability: TOO_LARGE` but return `413 RESPONSE_TOO_LARGE` if requested.
- Recheck canonical backing containment, node type, size, and SHA-256 before content response.
- Canonical evidence change/disappearance returns `409 ARTIFACT_CHANGED`.
- Insert no CORS headers; `OPTIONS` receives `405` after authority validation.

Every response includes:

```text
Cache-Control: no-store
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Cross-Origin-Resource-Policy: same-origin
X-Frame-Options: DENY
```

CSP:

```text
default-src 'self';
script-src 'self';
style-src 'self';
img-src 'self' data:;
connect-src 'self';
object-src 'none';
base-uri 'none';
frame-ancestors 'none';
form-action 'none'
```

Status mapping:

| HTTP | Meaning |
|---|---|
| `200` | Authorized route succeeded |
| `400` | Malformed request, missing/duplicate authority, encoding, or forbidden query/body shape |
| `403` | Host or Origin value rejected |
| `404` | Unknown route, record, or artifact |
| `405` | Method unsupported; include `Allow: GET, HEAD` |
| `409` | Canonical admitted artifact changed/disappeared |
| `413` | Request or response exceeded its limit |
| `500` | Sanitized unexpected failure |

All HTTP validation/routing/artifact errors, including static-route errors, use the closed JSON error schema and `application/json; charset=utf-8`. No error exposes traceback, unrecorded path, physical backing, inode, or device identity.

## Failure behavior

- Missing/unknown explicit root, invalid port, old schema, malformed explicit input, or oversized projection: no server, stderr, exit `2`.
- Unsafe node, intrinsic integrity failure, duplicate/conflicting identity, contained-descriptor failure, supplied relationship mismatch, failed diagnosis derivation, failed applied-refinement forward/inverse replay, or admission-time mutation: no server, stderr, exit `5`.
- Missing diagnosis subject, refinement diagnosis/base, or external corpus refinement: admit with `MISSING`; evaluation is `NOT_CHECKED`.
- Rejected refinement: diagnosis/base may be `MATCH` or `NOT_CHECKED`; derivation/reversibility are `NOT_APPLICABLE`.
- Invalid active installed package/lock/dependency/Python/extractor tuple: no command processing/server, exact active-runtime diagnostic on stderr, no stdout, exit `6`.
- Well-formed v0.5 artifact with an unknown `build_provenance.provenance_id`, a known-ID applicable-field mismatch, or a disallowed recorded `command_id`/`generator_id`: no verification JSON/server, exact unsupported-recorded-provenance diagnostic on stderr, exit `6`.
- Malformed recorded provenance: intrinsic schema/integrity failure, exit `5`.
- Missing/invalid bundled schema or provenance registry: invalid active runtime, exit `6`.
- Port unavailable: no server, sanitized stderr, exit `2`.
- Valid partial/failed observation, valid rejected refinement, or valid partial/failed corpus: admit and display its status.
- Browser-open failure: server continues.
- Canonical artifact mutation after admission: content request returns `409`.
- Noncanonical-copy mutation after admission: frozen projection remains; copy is never served; restart may reject it.
- Unexpected request failure: sanitized `500`; server remains available when safe.
- No old-artifact migration, compatibility mode, mixed-schema public session, or relationship replay against an absent record exists.
