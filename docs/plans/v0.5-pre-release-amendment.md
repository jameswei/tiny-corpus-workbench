# v0.5 Pre-release Amendment Plan

## Authority, premise, and outcome

This plan is the standalone current execution authority for the v0.5
pre-release amendment. Earlier correction plans and ledgers are historical
materials and do not contribute gates, scope, or implementation requirements
to this plan.

Baseline: clean `main` at
`8b04885a9471091cdfce17560e395a2d103d2806`; no `v0.5*` tag or GitHub
Release. The project remains learning-first, source-only, trusted-local, and
current-format-only. The Workbench remains read-only and loopback-only.

This amendment preserves immutable sources and raw extraction evidence,
diagnosis-not-authority, explicit human confirmation, proposal tamper/stale
detection, atomic publication, reversible lineage, corpus behavior, and
Workbench behavior. No retrospective outcome or retrospective artifact is
part of this work.

## Owner decisions, inferred requirements, and contract assessment

Owner-set:

- Two sequential implementation PRs: A, then B from green post-A `main`.
- PR A removes four verification-result Schemas and catalog entries. It
  replaces transient dictionary results with dependency-free dataclasses.
  Verifier stdout JSON and exit codes remain unchanged.
- PR B replaces editable decision JSON with proposal-only drafting and
  explicit `--approve` or `--reject`.
- The other 11 Schemas remain self-contained. `corpus-spec` is unchanged.
- Do not add Pydantic, an old-format reader or migration, a landing-page
  redesign, a hosted service, or a public API.
- Do not rewrite historical plans or released notes.
- Tag and GitHub Release remain separately authorized.

Resolved requirements:

- Keep `refinement-draft.schema.json` and its catalog key, but make the Schema
  root the proposal object.
- Persist canonical proposal bytes unchanged as `proposal.json`.
- `refinement-manifest.json` has required
  `decision: APPROVED|REJECTED` and no `status`.
- Proposal `state: REQUESTED` and transformation `state: APPLIED` remain
  lifecycle facts, not decision authorities.
- Transformation and history use `draft_id`. They contain no `decision_id`,
  `decided_by`, decision copy, or note.
- `refinement-manifest.json.decision` is the only machine-authoritative
  persisted decision field.
- `report.md` may render the decision as deterministic human-readable text.
  It is non-authoritative and contains no actor or note.
- No other persisted JSON or structured artifact copies the decision.
  Transient CLI and Workbench views may derive it directly from the manifest.
- All refinement consumers stop reading `manifest.status`.

Roadmap delta: none. Current CLI and internal record shapes change, but no
cross-version compatibility promise, public Python or HTTP API, deployment
model, or security posture is added.

## PR B — Proposal-only refinement and one persisted authority

**ID / branch:** PR-B / `work/v05-refinement-single-authority`

**Outcome:** Users inspect but never edit proposal JSON. Exactly one CLI flag
supplies the decision. Only the refinement manifest persists
machine-authoritative approval or rejection.

### Exact persisted matrix

| Manifest decision | Required persisted evidence | Forbidden |
| --- | --- | --- |
| `APPROVED` | `proposal.json`, `report.md`, `transformation.json`, `history.json`, `prepared/document.json`, `prepared/document.md`; non-null `revision_id`; transformation `state=APPLIED`; coherent proposal/draft, diagnosis, base, parent, artifact hashes, forward derivation, reversal, revision identity, and history tail | manifest `status`; another structured decision field; actor or note |
| `REJECTED` | `proposal.json`, `report.md`; `revision_id=null`; `parent=null`; derivation and reversal `NOT_APPLICABLE` | transformation, history, prepared directory or documents, `APPLIED`, another structured decision field, actor or note |

For approved observation bases, `parent=null`. For approved refinement bases,
`parent` is required and matches the base revision, run, manifest hash, and
prepared-document hash.

Artifact inventory, revision and parent behavior, verification states, corpus
eligibility, CLI output, and Workbench display branch solely from
`manifest.decision` plus coherent artifact presence.
`transformation.state=APPLIED` exists only for approved publications and
records execution, not authority.

### Exact proposal artifact

Every producer and consumer uses this descriptor:

```text
path: proposal.json
role: refinement-proposal
media_type: application/json
```

Remove `decision.json` and role `refinement-decision` from Schemas,
inventories, verifier logic, corpus and report links, Workbench admission and
projection, fixtures, tests, tools, and active documentation.

### Proposal byte freshness and safe capture

Resolution must:

1. Require the proposal path to identify one local, non-symlink regular file.
2. Capture its raw bytes and stable file identity using the existing safe
   regular-file mechanics. Retain enough identity evidence to detect
   replacement: device and inode where available, file kind, size,
   timestamps, and content hash or raw bytes.
3. Decode strictly as UTF-8 without a BOM, parse one JSON object, and validate
   it against the proposal Schema.
4. Snapshot diagnosis and base inputs, recompute the complete proposal from
   those inputs, and serialize it with project `canonical_json`: sorted,
   compact UTF-8 JSON plus exactly one final newline.
5. Require captured raw bytes to equal
   `canonical_json(recomputed_proposal)` exactly.
6. Reject reordered keys, changed whitespace, a BOM, non-UTF-8 or alternate
   encoding, missing or extra final newline, semantic edits, extra or missing
   fields, or stale diagnosis or base content.
7. Write the already verified captured bytes unchanged to staged
   `proposal.json`. Do not reserialize them.
8. Before atomic publication, recheck diagnosis and base snapshots and the
   proposal path and file identity. Re-read through the safe regular-file
   path or retained descriptor and require the same kind, identity, raw
   bytes, and hash. Removal, replacement, even with equivalent JSON, or
   concurrent mutation fails.
9. On any failure, remove staging, publish nothing, and leave proposal,
   diagnosis, and base unchanged.

A change after the final successful recheck cannot alter the captured staged
bytes. Publication remains based only on the verified capture.

### Deterministic report

`report.md` is a human-readable derived artifact. It may show `APPROVED` or
`REJECTED`, proposal or draft identity, finding and refiner, and revision
identity when applicable. It contains no actor or note and is never consulted
as authority.

The verifier must regenerate its exact bytes from the authoritative manifest
plus proposal and applicable transformation or revision evidence, then
compare them with persisted `report.md`. A mismatch, unexpected text, or
tampering is an integrity failure. Tests cover approved and rejected
regeneration and report-only tampering.

### Exact CLI stdout contracts

Parser help and metavars use `PROPOSAL_FILE` and proposal terminology.

`draft-refinement --output PROPOSAL_FILE` prints compact UTF-8 JSON with
`sort_keys=True`, resolved absolute-path strings, and one final newline:

```json
{"draft_id":"<64-lowercase-hex>","proposal":"/absolute/resolved/proposal.json"}
```

`proposal` is the resolved filesystem path supplied through `--output`.

Approved resolution prints in lexical key order:

```json
{"decision":"APPROVED","manifest":"/absolute/resolved/refinement-manifest.json","revision_id":"<64-lowercase-hex>","run_id":"<run-id>"}
```

Rejected resolution uses the same stable shape:

```json
{"decision":"REJECTED","manifest":"/absolute/resolved/refinement-manifest.json","revision_id":null,"run_id":"<run-id>"}
```

There is no `status` key. Success remains exit `0`. Existing input, integrity,
runtime, and internal exit meanings remain `2/5/6/1`.
