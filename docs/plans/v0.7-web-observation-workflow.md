# v0.7 — Web Observation Workflow Implementation Plan

## Summary

v0.7 makes observation the first document workflow available directly in the Local Visual Workbench.

A learner can start `corpus workbench` from a clean checkout, run the guided `policy-memo.md` example or upload one supported document, follow honest stage-level progress, and inspect the published observation without using the CLI.

The implementation remains local and lightweight:

- reuse the existing observation application service;
- retain the sequential loopback HTTP server;
- add one background observation worker;
- publish immutable inputs and observations into the selected workspace;
- keep job state in memory only;
- preserve transactional Workbench refresh;
- change no persisted record schema and add no dependency.

One atomic feature PR must contain implementation, tests, learning/public documentation, website copy, version metadata, and release notes.

## Interfaces and behavior

### CLI and workspace

Extend the existing command to:

```text
corpus workbench
  [--workspace WORKSPACE]
  [--docling-artifacts MODEL_DIRECTORY]
  [--port PORT]
  [--no-open]
```

- `--docling-artifacts` defaults to `.cache/docling/models`, matching `corpus observe`.
- Create the selected workspace and missing parents at startup.
- Require the workspace to be a readable, writable, searchable directory.
- Web observations publish under `WORKSPACE/extraction-observatory/`.
- Uploaded inputs are stored immutably at:

```text
WORKSPACE/inputs/<sha256>/<original-filename>
```

- Accept one `.docx`, `.md`, `.pdf`, or `.txt` file up to exactly `33,554,432` bytes.
- Validate the filename as one filesystem component: reject empty names, `.`, `..`, NUL, `/`, `\`, unsupported suffixes, or names longer than the filesystem-safe UTF-8 limit.
- Write and validate an upload in a temporary entry under `inputs/`, then atomically publish it to its content-addressed path.
- Reuse an existing regular file only when the target bytes match. Never overwrite.
- Keep an accepted input even if its later observation job fails, so the original submitted evidence remains inspectable and retryable from the filesystem.
- Observe the committed `fixtures/golden/policy-memo.md` directly for the guided path; do not duplicate it under `inputs/`.

### Observation progress and job model

Extend the existing `observe(...)` application service with an optional progress callback. The CLI passes no callback and retains its current arguments, stdout, exit codes, publication behavior, and error behavior.

Emit only these real stages, in order:

```text
PREPARING_SOURCE
EXTRACTING_DOCLING
EXTRACTING_MARKITDOWN
BUILDING_EVIDENCE
VERIFYING_AND_PUBLISHING
```

These five values come from the shared observation service. After `observe(...)`
returns a published path, the Web job manager uses one additional
`REFRESHING_WORKSPACE` stage while it runs the transactional refresh.

Add lightweight Python dataclasses for the in-process Web job payload; do not add JSON Schema.

Maintain one current/latest job with exactly these fields:

| Field | Value |
| --- | --- |
| `job_id` | Opaque lowercase UUID hex |
| `state` | `QUEUED`, `RUNNING`, `COMPLETED`, or `FAILED` |
| `stage` | `null`, one observation stage, or `REFRESHING_WORKSPACE` |
| `input` | `{kind, name, media_type, size, sha256}` where kind is `GUIDED` or `UPLOAD` |
| `observation` | `null` or `{status, observation_id, record_key}` where status is `SUCCESS`, `PARTIAL_SUCCESS`, or `FAILED` |
| `refresh` | `null` or `{status, message}` where status is `READY` or `FAILED` |
| `error` | `null` or `{code, message}` |

Execution rules:

- Use one background worker and a queue capacity of one.
- Permit only one active job. Reject a second submission with `OBSERVATION_BUSY`.
- Replace the previous terminal job when a new job is accepted.
- Permit only these transitions:
  1. acceptance creates `QUEUED` with `stage = null`;
  2. the worker moves it to `RUNNING` through the five callback stages;
  3. publication keeps it `RUNNING` with `REFRESHING_WORKSPACE`;
  4. refresh success produces `COMPLETED`, `stage = null`,
     `refresh.status = READY`, and the resolved `record_key`;
  5. refresh failure produces `COMPLETED`, `stage = null`,
     `refresh.status = FAILED`, and `record_key = null`;
  6. an exception before publication produces `FAILED`, `stage = null`,
     `observation = null`, `refresh = null`, and one accepted-job error.
- Terminal jobs do not change. A published record is terminally `COMPLETED`
  regardless of its observation status or observation-service exit code.
- Do not persist job state, history, progress, or errors.
- Do not support cancellation or parallel jobs.
- On shutdown, stop accepting work and wait for the active observation to finish its atomic publication.
- Keep the existing sequential `HTTPServer`; do not introduce a general threaded server.
- Protect job snapshots and Workbench refresh/projection replacement with locks. Serialize manual and automatic refreshes.
- A manual refresh during extraction may complete against the pre-publication workspace; the job’s automatic refresh runs after publication.

Job and record outcomes remain separate:

- `COMPLETED` means an observation record was published, including records whose own status is `PARTIAL_SUCCESS` or `FAILED`.
- `FAILED` means no observation record was published.
- Missing or invalid PDF models remain ordinary published observation evidence when the existing service publishes such a record.
- After publication, run the existing complete-workspace transactional refresh.
- On refresh success, set `refresh.status = READY`, resolve the new `record_key`, and expose it for automatic selection.
- On refresh failure, keep the job `COMPLETED`, set `refresh.status = FAILED`, leave `record_key` null, retain the last accepted projection, and do not remove the new observation.

### Internal HTTP bridge

Add these bundled-UI routes:

```text
GET or HEAD /api/observation-jobs
POST /api/observation-jobs/guided
POST /api/observation-jobs/upload?filename=<percent-encoded-name>
```

`GET /api/observation-jobs` returns canonical JSON containing:

- guided fixture metadata for `policy-memo-md`;
- supported extensions and `max_bytes = 33554432`;
- the current/latest job or `null`.

Submission behavior:

- Guided submission requires an empty body.
- Upload submission requires one decimal `Content-Length`, no transfer encoding, a nonempty body, and a valid filename query.
- Decode the query as strict UTF-8 percent-encoding. Require exactly one
  nonempty `filename` value and no other query field. Reject malformed escapes.
- Limit the decoded filename to 255 UTF-8 bytes in addition to the
  single-component rules above.
- Do not trust the request media type; derive and validate format from the filename and file content.
- Return `202` with `{"job": <job>}` when accepted.
- Return the existing two-field stable error payload for failures.
- Use the exact HTTP error mapping below:

| Code | Status | Meaning |
| --- | ---: | --- |
| `INVALID_REQUEST` | 400 | Malformed query, filename, body framing, or guided body |
| `INVALID_SOURCE` | 400 | Unsupported suffix or content that fails existing source validation |
| `NOT_FOUND` | 404 | Unknown route or existing opaque record/artifact key |
| `METHOD_NOT_ALLOWED` | 405 | Method outside the route contract |
| `OBSERVATION_BUSY` | 409 | One job is already queued or running |
| `WORKSPACE_UNAVAILABLE` | 409 | The selected workspace cannot accept an input or publication |
| `WORKSPACE_REFRESH_FAILED` | 409 | Existing manual refresh rejected its complete candidate |
| `UPLOAD_TOO_LARGE` | 413 | Declared upload size exceeds 32 MiB |
| `RESPONSE_TOO_LARGE` | 413 | Existing Workbench response limit was exceeded |
| `INTERNAL_ERROR` | 500 | Sanitized unexpected request-processing failure |

- Before publication, report accepted-job failures through later job snapshots
  rather than changing the returned `202`. Map `InputError` to
  `OBSERVATION_INPUT_FAILED`, `IntegrityError` to
  `OBSERVATION_INTEGRITY_FAILED`, `RuntimeContractError` to
  `OBSERVATION_RUNTIME_FAILED`, and any other exception to
  `OBSERVATION_INTERNAL_FAILED`. All messages are sanitized.
- Any exception after publication is a refresh failure rather than a job
  failure: keep `COMPLETED`, set `refresh.status = FAILED` with a sanitized
  message, retain the last accepted projection, keep the published
  observation, and leave `record_key = null`.
- Reject oversized requests before reading their body.
- Preserve exact GET/HEAD parity.
- Keep all routes internal to the bundled UI; do not create persisted payload schemas.
- Do not add `Origin`, `Host`, CSRF-token, or custom-header authority checks.
  The trusted-local model accepts that another local process or an unrelated
  webpage may trigger a state-changing loopback request without reading its
  response. Return no CORS headers and do not present loopback binding as an
  access-control boundary.

`GET /api/observation-jobs` returns this exact envelope:

```text
{
  "capabilities": {
    "guided": {"id", "name", "media_type"},
    "upload": {"extensions": [".docx", ".md", ".pdf", ".txt"], "max_bytes": 33554432}
  },
  "job": null | <job>
}
```

### Workbench interface

Replace the global “Read only” claim with wording that distinguishes workflow execution from record immutability.

Add one observation panel with:

- a guided **Observe policy memo** action;
- a single-file picker with accepted extensions and a visible 32 MiB limit;
- source metadata only: filename, format, size, and SHA-256;
- job state and current real stage;
- observation status and refresh outcome;
- accessible error and warning messages.

Interaction rules:

- Disable both submission controls while a job is active.
- Poll `/api/observation-jobs` at a fixed short interval only while the job is `QUEUED` or `RUNNING`.
- Recover the current/latest job after a browser reload.
- Stop polling at a terminal state.
- After `COMPLETED` plus `READY`, reload the Workbench projection and automatically select the returned observation record.
- After `COMPLETED` plus refresh failure, keep the existing record view and explain that publication succeeded but the current projection rejected the complete candidate.
- Keep record navigation and existing literal artifact retrieval available during observation.
- Do not display percentage progress.
- Do not render or serve the uploaded original file.
- Add no frontend framework, format renderer, remote resource, browser storage, WebSocket, or additional static asset file.
- Continue using text-only DOM construction, keyboard focus management, and the existing polite live region.

## Test and acceptance plan

The release candidate passes when all of the following hold:

1. From a clean checkout with no `build/`, `corpus workbench --no-open` creates the workspace and serves successfully.
2. The guided policy memo completes without PDF models, publishes one immutable observation, refreshes the workspace, and opens the new record.
3. A valid uploaded Markdown file is preserved at its SHA-256 input path and produces inspectable Docling, MarkItDown, canonical, and comparison evidence.
4. Exactly 32 MiB is accepted at the transport boundary; 32 MiB plus one byte returns `413` without publication.
5. Invalid names, unsupported formats, empty/invalid content, malformed lengths, and transfer encoding publish neither input nor job.
6. A duplicate accepted input is reused without overwrite; every observation still receives a new immutable run.
7. A second submission during active work returns `409`; a new submission after a terminal job replaces the previous in-memory job.
8. All five stages appear in real order, and neither payload nor UI contains percentage progress.
9. Published `SUCCESS`, `PARTIAL_SUCCESS`, and `FAILED` observation records all yield `COMPLETED` jobs; exceptions before publication yield `FAILED`.
10. A failed automatic refresh preserves the previous projection and the newly published record on disk while reporting both outcomes accurately.
11. Browser reload restores the latest in-memory job; process restart clears jobs but retains inputs and published records.
12. Uploaded originals are not exposed through an HTTP route or rendered in the browser.
13. Existing CLI observation, verification, workspace admission, manual refresh, record detail, and artifact tests remain unchanged in behavior.
14. Unit tests, model-free integrations, existing model-dependent extraction coverage, asset/site validators, compilation, fixture checks, checkout portability, and `git diff --check` all pass.
15. A manual local walkthrough verifies guided observation, upload observation, stage feedback, automatic selection, keyboard use, narrow layout, and clear failure messages.

Validation evidence has distinct consumers and purposes:

| Gate | Purpose |
| --- | --- |
| Local task checks | Give the builder fast evidence for the changed task and preserve accepted checkpoints |
| Local cumulative checks | Exercise the complete browser-to-publication flow and all changed machine consumers before PR publication |
| PR Fast | Reproduce unit, model-free integration, asset, site, portability, and diff hygiene on the synthetic merge candidate |
| PR Full | Reuse existing pinned-model extraction/diagnosis/corpus evidence; add no duplicate Web PDF run because Web calls the same observed service |
| Exact-main smoke | Prove the merged source starts the CLI and completes one guided Web observation on the exact merge state |
| Pages | Validate and deploy only the changed static public site |
| Release | Verify tag target, GitHub Release metadata, and generated source archive rather than rerunning earlier tests |
| Scheduled | Add none; v0.7 has no time-dependent or external-state behavior that needs distinct scheduled coverage |

Evidence may be reused only when its command, result, source revision, inputs,
and consumer purpose remain applicable. Code, dependency, fixture, generated
asset, or CI-consumer changes invalidate the affected evidence. Human-facing
README, guide, lesson, landing-page, CURRENT, and release-note claims receive
human review against owner intent; those prose surfaces are not machine
contracts.

## Settled owner decisions

- The guided fixture is `fixtures/golden/policy-memo.md`.
- Browser upload limit is exactly 32 MiB.
- Uploaded inputs persist immutably under the workspace; guided fixtures remain repository-owned.
- The browser displays uploaded-source metadata but not original content.
- The Workbench gains observation authority only. Published records remain immutable, and diagnosis/refinement/corpus workflows remain separate.
- Job state is single-worker, single-active, latest-only, in-memory, and non-cancellable.
- A published observation remains a `COMPLETED` job when complete-workspace refresh fails; the refresh failure is reported separately and the last accepted projection remains.
- The trusted-local Workbench adds no request-origin or CSRF gate. The owner
  accepts possible cross-origin triggering of loopback writes as a low-risk
  local resource effect rather than adding authentication-like machinery.

## Implementation defaults and unchanged premises

- The CLI retains current observation behavior and calls the shared service without a progress callback.
- The sequential loopback server remains; one worker and explicit locks add only the concurrency needed for observation.
- The implementation adds no dependency and changes no persisted record schema.
- The internal HTTP shapes are bundled-UI implementation contracts, not a new public or cross-version compatibility promise.
- Source-only local deployment remains unchanged. The trusted-loopback posture
  changes by granting local observation/input-write authority without treating
  request origin as an authority boundary; binding remains local and uploaded
  originals are not served.
- Persisted record schemas and observation semantics remain unchanged.
