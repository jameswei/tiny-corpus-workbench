# v0.8 — Interactive Document Lifecycle

## Summary

v0.8 completes the single-document preparation lifecycle in the Local Visual Workbench:

```text
observe
  → verify
  → diagnose
  → inspect finding
  → create proposal
  → approve or reject
  → inspect immutable refinement and revision history
```

Browser and CLI share application services/workspace records. Add no public API, dependency, persisted schema, auto-repair, or JSON-editing workflow.

Deliver code, tests, docs, versions, CI, and release preparation in one atomic feature PR with semantic checkpoints.

## Decision and contract classification

Owner decisions are the complete browser lifecycle, browser-primary decisions, both guided examples, visible admission verification, D007/R002, D009/R001, and D010/R003 support, synchronous lifecycle actions beside the observation job, persisted drafts, unchanged-CLI continuation, exact root/error behavior, the same-UI token, internal loopback HTTP, and one atomic v0.8.0 PR.

Repository-derived requirements are transactional admission, re-admission before mutation, existing immutable publication/verification services and schemas, canonical JSON, fixed workspace families, stable errors, current CLI arguments, and text-only DOM construction.

Roadmap delta: implement existing v0.8 only. Add no corpus/RAG execution, dependency, public API/schema, hosted/remote deployment, authentication, or compatibility/migration promise.

Owner-approved contract classification:

- `WORKSPACE/refinement-drafts/` is documented current behavior without a cross-version location or reader promise.
- The four CLI paths are bundled-UI metadata over unchanged CLI behavior, not a public HTTP contract.
- The process-local token covers only new lifecycle POSTs. It blocks ordinary cross-origin forms, not local processes, and creates no public security contract. Observation and manual refresh are unchanged.

## Key implementation changes

### 1. Actionable workspace snapshot

The accepted snapshot atomically owns the frozen projection/details and a `record_key → actionable root token` index for verified top-level observation, diagnosis, and refinement records. Each token records a safe workspace-relative path, canonical root, and accepted directory device/inode. The workspace and every descendant component through the contained canonical root must be real non-symlink directories. Token presence permits safe resolution; kind, relationship, decision, and artifact availability still determine action eligibility.

Rules:

- Only top-level records can be action candidates. An observation is diagnosable only when its admitted Docling artifacts include canonical `docling-document-json` content usable by the existing diagnosis service. Determine this from admitted artifact availability, not overall status: a `FAILED` observation or MarkItDown-only `PARTIAL_SUCCESS` remains inspectable but cannot be diagnosed; `PARTIAL_SUCCESS` with Docling canonical output remains diagnosable even if MarkItDown failed. Corpus-contained records remain inspectable only.
- After coordinator acquisition, capture one snapshot. For every required root, resolve its stored relative path without following symlinks; recheck containment and device/inode; re-admit it; and match its record key. Changed, missing, moved, symlinked, or byte-identically replaced roots return `WORKSPACE_STALE`, publish nothing, and require refresh.
- Diagnose an eligible observation or approved refinement. A direct request for an observation without canonical Docling content returns `409 ACTION_NOT_AVAILABLE` and publishes nothing. Derive a proposal base from `DIAGNOSIS_SUBJECT = MATCH`; resolve from the draft context's accepted diagnosis/base keys. The browser supplies no paths.
- Observation and an approved refinement can be diagnosis subjects.
- A rejected refinement is display-only because it has no prepared revision.
- A failed refresh preserves both accepted projection and root index.

Retain the v0.7 policy-memo observation example and add the model-free lifecycle example `fixtures/refinement/whitespace-cleanup.md`.

Generalize the internal guided-observation route:

```text
GET or HEAD /api/observation-jobs
POST /api/observation-jobs/guided/{guided_id}
```

`GET /api/observation-jobs` retains its current envelope and upload capability. Replace `capabilities.guided` with this ordered array:

```text
[
  {"id": "policy-memo-md", "name": "policy-memo.md", "media_type": "text/markdown"},
  {"id": "whitespace-cleanup-md", "name": "whitespace-cleanup.md", "media_type": "text/markdown"}

```

Both POSTs use an empty body and existing job behavior. Remove the singular route without an alias.

Verification is not a new job or record:

- Admission continues intrinsic verification; observation detail says `Verified during workspace admission`.
- Diagnosis and refinement details retain their existing relationship, derivation, and reversibility states.
- Unverified records are never actionable. Add no Verify button or open-time verification.

### 3. Lifecycle coordinator and application service

Add one application component for diagnosis publication, canonical proposal/preview, approve/reject resolution, automatic refresh, and result selection. Reuse diagnosis/refinement services; never call CLI parsers or duplicate domain logic in HTTP or JavaScript. Observation remains the background job; lifecycle actions run synchronously on the sequential handler.

Add one non-blocking lifecycle operation coordinator:

- Observation acceptance atomically transfers ownership to queued work. While its worker owns it, routed requests return `OBSERVATION_BUSY` for observation or `LIFECYCLE_BUSY` for lifecycle. Failed acceptance releases immediately; worker `finally` releases once after every terminal outcome.
- Synchronous lifecycle acquires before snapshot and releases in `finally`. The sequential handler routes nothing else meanwhile: observation or lifecycle arrivals wait, then use post-release state without arrival-time busy.
- Observation and lifecycle mutations cannot overlap.
- Manual refresh during background observation retains v0.7 transactional behavior; during synchronous lifecycle it waits like every request.
- Shutdown waits for an active synchronous handler; observation shutdown still stops acceptance, waits for its atomic publication path, and leaves no ownership.
- Keep `HTTPServer`; add no `ThreadingHTTPServer`, worker, concurrent dispatcher, job history, cancellation, WebSocket, or persistent job state.
- Deliberate repeated resolution may publish separate immutable records. UI prevents accidental duplicates; add no idempotency ledger.

### 4. Canonical draft storage

Store Workbench-created proposals at:

```text
WORKSPACE/refinement-drafts/<draft_id>.json
```

Creation rules:

- Prepare a contained, readable/writable/searchable, non-symlink `refinement-drafts/`; reject symlink/non-directory components. Draft through the existing service into private same-filesystem staging.
- Validate schema, canonical bytes, and content-derived `draft_id`. Size-check the response before publication; `RESPONSE_TOO_LARGE` cleans staging and creates no draft/context.
- Publish atomically without overwrite. Reuse an existing no-follow, stable regular file only for identical canonical bytes; retain it after either decision.
- Drafts use the existing `refinement-draft` schema but are not workspace records or catalog entries.

Persisted `draft_id` remains proposal identity. Compute process-local `draft_key` as lowercase 64-hex SHA-256 of canonical JSON over exactly `{"draft_id": draft_id, "diagnosis_record_key": diagnosis_record_key, "base_record_key": base_record_key}`; map it to those values. Exact context reuses the key; equivalent bytes under another diagnosis get another key without alias/overwrite. Resolution requires `draft_key`, fresh context roots, stable canonical draft, and service recomputation; live-context draft mismatch is `WORKSPACE_STALE` without publication.

Reload may recreate/reuse the exact context. Restart restores neither context nor panel; an unknown live `draft_key` is `NOT_FOUND`. Recreate from diagnosis or continue by CLI.

Each key's expandable `cli_continuation` supplies its exact resolved `proposal_path`, `diagnosis_path`, `base_path`, and `output_root_path` (`WORKSPACE/controlled-revisions`) for unchanged `corpus resolve-refinement PROPOSAL --diagnosis DIAGNOSIS --base BASE --output-root OUTPUT --approve|--reject`. This is secondary internal UI metadata.

### 5. Internal lifecycle bridge

Add these bundled-UI-only routes:

```text
GET or HEAD /api/lifecycle/action-token
POST /api/lifecycle/diagnoses/{subject_record_key}
POST /api/lifecycle/proposals/{diagnosis_record_key}/{finding_id}
POST /api/lifecycle/proposals/{draft_key}/approve
POST /api/lifecycle/proposals/{draft_key}/reject
```

At startup generate a 256-bit process-local `secrets.token_urlsafe(32)` token. Same-origin `GET /api/lifecycle/action-token` returns `200` canonical `{"action_token": string}`; `HEAD` keeps status/headers but no body. Both send `Cache-Control: no-store`, no CORS. Local processes can still fetch/use it.

Every lifecycle POST requires exactly one matching `X-TCW-Action-Token`. Missing, duplicate, wrong, or pre-restart values return `403 ACTION_TOKEN_INVALID` before coordination, reads, drafts, or publication. Never put the token in URL/body/log/storage/disk. On recognized POSTs, framing precedes token validation: malformed framing is `INVALID_REQUEST`; well-framed invalid token is `ACTION_TOKEN_INVALID`.

Lifecycle POSTs require empty bodies and lowercase 64-hex path IDs; reject transfer encoding, nonzero/ambiguous length, queries, and extra segments. Wrong method on a known route is `405 METHOD_NOT_ALLOWED` with `Allow`; unknown/malformed route or key is `404 NOT_FOUND`.

Order: route/method → framing → token → non-blocking coordinator → key/context eligibility → root/draft freshness → domain operation → publication → refresh/result lookup.

Successful lifecycle POSTs return `200`, including publication plus refresh failure. Python composes canonical JSON; add no schema.

Diagnosis response:

```text
{
  "publication": {
    "kind": "DIAGNOSIS",
    "run_id": string,
    "record_key": string | null
  },
  "refresh": {
    "status": "READY" | "FAILED",
    "message": string | null
  }
}
```

Proposal response:

```text
{
  "draft": {
    "draft_key": string,
    "draft_id": string,
    "diagnosis_record_key": string,
    "base_record_key": string,
    "finding": {
      "finding_id": string,
      "rule_id": string,
      "summary": string
    },
    "refiner": {
      "refiner_id": string,
      "name": string,
      "version": string
    },
    "affected_refs": [string],
    "edits": [
      {"target": object, "before": value, "after": value}
    ],
    "cli_continuation": {
      "proposal_path": string,
      "diagnosis_path": string,
      "base_path": string,
      "output_root_path": string
    }
  }
}
```

Resolution response:

```text
{
  "publication": {
    "kind": "REFINEMENT",
    "decision": "APPROVED" | "REJECTED",
    "run_id": string,
    "revision_id": string | null,
    "record_key": string | null
  },
  "refresh": {
    "status": "READY" | "FAILED",
    "message": string | null
  }
}
```

Before-publication failure creates no record. After publication, refresh failure returns the identity with `record_key = null` and `refresh.status = FAILED`, retains the directory and prior projection, and permits later manual admission.

Extend the current stable two-field error payload with:

- `ACTION_TOKEN_INVALID` — `403`, the lifecycle action token is missing or invalid;
- `LIFECYCLE_BUSY` — `409`, a lifecycle POST was rejected because background observation owns mutation coordination;
- `ACTION_NOT_AVAILABLE` — `409`, selected kind, relationship, finding, refiner, or decision context is ineligible;
- `WORKSPACE_STALE` — `409`, an accepted action input changed before execution.

Exact mapping:

- `ACTION_NOT_AVAILABLE`: contained record, observation without admitted canonical Docling content, rejected refinement, missing/non-`MATCH` relationship, unsupported finding/refiner, no-findings diagnosis, or other ineligible action.
- `WORKSPACE_STALE`: missing/changed/moved/symlinked/replaced accepted root, or missing/tampered/mismatched draft with live context.
- `NOT_FOUND`: unknown opaque key, malformed action route, or well-formed `draft_key` without live process context.
- Existing meanings remain for `INVALID_REQUEST`, `WORKSPACE_UNAVAILABLE`, `RESPONSE_TOO_LARGE`, `INTERNAL_ERROR`, `OBSERVATION_BUSY`, `INVALID_SOURCE`, `UPLOAD_TOO_LARGE`, and `WORKSPACE_REFRESH_FAILED`; only observation-worker ownership rejecting a lifecycle POST uses `LIFECYCLE_BUSY`.

Sanitize messages. After diagnosis/refinement publication, refresh/admission/lookup failure must use the success response's failed-refresh outcome, never an error payload that hides publication.

### 6. Finding capability and proposal preview

Enrich each diagnosis finding in the internal detail payload with:

```text
refiner: null | {refiner_id, name, version}
proposal_action: {
  status: "AVAILABLE" | "UNAVAILABLE",
  reason: null | "NO_SUPPORTED_REFINER" | "SUBJECT_NOT_ACTIONABLE"
}
```

`refiner` is application-catalog capability. `proposal_action` is workspace eligibility: `AVAILABLE` requires that capability and an admitted `DIAGNOSIS_SUBJECT = MATCH` top-level actionable base, with reason `null`. Unsupported uses `NO_SUPPORTED_REFINER`; supported with contained, missing, non-`MATCH`, or non-actionable subject uses `SUBJECT_NOT_ACTIONABLE`. Backend recomputes eligibility and root freshness; direct ineligible calls are `ACTION_NOT_AVAILABLE`. JavaScript duplicates no logic.

Expose these supported mappings:

- D007 → Repeated boilerplate removal (R002)
- D009 → Whitespace normalization (R001)
- D010 → Deterministic dehyphenation (R003)

UI rules:

- Show the human-readable rule/refiner name first and the ID as secondary technical information.
- `AVAILABLE`: show `Refiner available` and **Create proposal**.
- `NO_SUPPORTED_REFINER`: show `Diagnosis only · No supported deterministic refiner` and no control.
- `SUBJECT_NOT_ACTIONABLE`: keep the refiner capability visible, show no control, and say `Proposal unavailable · diagnosis subject is not actionable in this workspace`.
- The guided lifecycle demonstrates D009/R001, but ordinary admitted records can use all three supported refiners.
- D009 and D010 proposals show readable text before/after values.
- D007 shows the structural movement from `body` to `furniture`, affected references, indices, and parent references.
- Construct all proposal evidence with text-only DOM APIs. Do not execute markup or add format-specific renderers.

### 7. Browser lifecycle experience

Add a focused **Document lifecycle** area; keep **Observe policy memo** and add **Start whitespace lifecycle**.

- Fetch the same-origin token into memory. If unavailable, disable lifecycle controls and show an error; observation/manual refresh remain usable.
- Show **Diagnose document** for diagnosable observations and approved refinements. An observation without canonical Docling content instead shows `Diagnosis unavailable · canonical document is not available`.
- After diagnosis, refresh/select it. For `proposal_action = AVAILABLE`, create and display the proposal without JSON editing.
- Approve/reject use `draft_key`; persisted identity remains `draft_id`. Show separate **Approve proposal** and **Reject proposal** controls.
- A token-bearing click supplies the human decision to the resolution service. Only `refinement-manifest.json.decision` is persisted authority; token, `REQUESTED`, UI/HTTP, and transformation states are not.
- Disable mutation controls before fetch and until response; a synchronous request may wait behind the current handler. Never retry state changes. On `ACTION_TOKEN_INVALID`, refetch if possible but never replay; require another click.
- After resolution, refresh/select it. Approved detail shows verification, transformations, reversibility, history, and **Diagnose prepared revision**; rejected detail says no revision and cannot continue.
- Refresh failure preserves the view and explains that publication succeeded but needs later refresh. Keep the four CLI paths/command in expandable technical details.
- Preserve keyboard/focus, polite announcements, narrow/reduced-motion layout, literal rendering, and local-only fetches. Add no framework, browser storage, remote resource, or asset.

### Bounded temporal scenario matrix

| Existing state | Attempted action | Required result |
| --- | --- | --- |
| Idle | Start observation | Accepted background job |
| Observation queued/running | Start another observation | `409 OBSERVATION_BUSY` |
| Observation queued/running | Diagnose, draft, approve, or reject | `409 LIFECYCLE_BUSY` |
| Synchronous lifecycle handler active | Any later HTTP request | Connection waits; after release it routes against new current state, without arrival-time busy |
| Observation running | Manual refresh | Transactional pre-publication or current snapshot; no partial record |
| Publication complete | Automatic refresh | New record selected on success |
| Publication complete, refresh rejected | Any action result | Publication retained; old projection retained |
| Lifecycle request fails before publication | Next action | Coordinator released; no record created |
| Observation reaches any terminal state | Next lifecycle action | Coordinator released; action accepted |
| Browser sends a successful decision | UI receives result | Controls remain disabled for that completed proposal view |
| Server restarts after UI loaded a token | UI attempts an old authorized request | `ACTION_TOKEN_INVALID`; no replay; a new click is required |
| Server shuts down with observation active | Shutdown | Stop accepting work and wait for atomic publication path |
| Server shutdown with lifecycle handler active | Shutdown | Wait for the synchronous handler to finish |
