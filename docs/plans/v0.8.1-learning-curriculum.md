# v0.8.1 — Learning Curriculum Refresh

## Status and intent

This pre-implementation plan needs a fresh independent `PASS` with zero
findings and owner approval of its exact reviewed hash.

v0.8.1 is a docs-focused, source-only patch. It replaces eight
milestone-named lessons with five lessons organized around the current
document lifecycle. It changes version metadata to `0.8.1` but does not change
product behavior.

The target reader is a technical learner who can use a terminal, a virtual
environment, and basic JSON. The curriculum teaches corpus-preparation
concepts, evidence, authority, and practical inspection. It does not teach
Python or shell fundamentals.

## Curriculum

`learning/README.md` remains the learning entry point, common setup, shared
glossary, and five-topic map. Put complete setup there once. After `.venv`
activation, use `corpus ...` for learner commands. Use `uv` only for
environment synchronization and conditional model download.

The hub must state:

- lessons 1, 2, 3, and the guided lesson-5 path are model-free;
- PDF observation is an optional lesson-1 extension;
- prefetched Docling models are required for a `COMPLETE` run of either
  committed corpus specification;
- a missing-model corpus run can still publish a valid `PARTIAL` record.

Each lesson contains, when useful: purpose, objectives, terms, mental model,
prerequisites, guided exercise, evidence to inspect, expected results, safe
counterexample, knowledge check, answers, and next step. Omit sections that
would be filler.

### 1. `learning/observe-extraction.md`

Teach:

- raw source, private snapshot, extraction views, canonical
  `DoclingDocument`, and observation record;
- one model-free Markdown CLI exercise and independent verification;
- descriptive Docling-versus-MarkItDown comparison without quality ranking;
- artifact integrity, current-source/model freshness, and authenticity as
  separate questions;
- guided and uploaded Workbench observation as alternative entries to the
  same observation service;
- optional PDF extraction, local model inventory, offline observation, and
  missing-model evidence;
- one copied-record integrity experiment.

### 2. `learning/diagnose-with-evidence.md`

Teach:

- rules, findings, severity, document references, and closed evidence shapes;
- diagnosis and independent verification of a published observation;
- D002 and structural findings as different evidence forms;
- the limited meaning of `NO_FINDINGS`;
- diagnosis as read-only fact recording, never mutation authority;
- equivalent CLI and Workbench behavior.

### 3. `learning/control-document-revision.md`

Teach:

- finding-to-refiner mapping, proposal, explicit decision, immutable revision,
  lineage, derivation, and reversal;
- D009/R001 drafting, approval, rejection, and refinement verification;
- proposal files as read-only suggestions;
- CLI flags and Workbench actions as ways to supply the decision;
- `refinement-manifest.json.decision` as the only persisted structured
  decision authority;
- exact evidence differences between approved and rejected records;
- one copied-record integrity experiment.

### 4. `learning/inspect-a-corpus.md`

Teach:

- explicit specification, member, snapshot, aggregate summary, and static
  report;
- why both committed specifications need models for `COMPLETE`;
- complete golden and quality corpus execution when models are available;
- the golden matrix's 12 members and exact D009 outcome;
- the quality corpus's five members and exact D002, D003, D004, D005, D007,
  D009, and D010 coverage;
- a missing-model run that publishes `PARTIAL`, followed by self-contained
  verification;
- `COMPLETE`, `PARTIAL`, and `FAILED` meanings;
- source-text-free aggregation, descriptive extractor differences, and
  explicit approved-revision inclusion;
- historical integrity versus optional live specification/source/model
  advisories;
- corpus inspection as CLI-only and unable to discover inputs, create
  refinements, or authorize changes.

Never describe a complete committed-specification run as model-free.
`verify-corpus` is model-free only after a corpus record exists.

### 5. `learning/complete-document-lifecycle.md`

Use the guided Workbench whitespace path to teach observation, admission
verification, diagnosis, proposal, approval or rejection, and revision
inspection. Map page actions to the concepts and persisted records from the
first four lessons.

Also teach the shared workspace, manual transactional refresh, uploaded
inputs, latest in-memory job, immutable published records, record selection,
diagnosis-owned proposal state, CLI continuation, and Workbench inspection of
all record families. Explain the action token, loopback binding, and
trusted-local boundary without calling them authentication.

Preserve these observable temporal rules:

- only one observation job runs at a time;
- the page polls snapshots and can miss a fast stage live;
- an ordered stage can appear complete without claiming the browser observed
  it live;
- reload restores the latest job only while the same server process remains;
- restart clears the job, action token, and proposal panels but retains
  accepted inputs, draft files, and published records;
- observation and lifecycle publication do not overlap;
- lifecycle actions are not retried automatically;
- refresh failure retains the last accepted projection while a successfully
  published record remains on disk.

## Validation and evidence

Maintain an uncommitted claim-to-evidence checklist under `/tmp`. Map behavior
claims to help, code, tests, fixtures, or current guides.

Validation purposes are distinct:

- **Local:** Check every literal command and option against help; run the
  model-free observation, diagnosis, approve, reject, verification, guided
  Workbench, and missing-model `PARTIAL` journeys in isolated workspaces;
  check the complete-corpus command boundary; run existing unit, model-free
  integration, installed-runtime lifecycle, fixture, corpus-specification,
  Workbench-asset, site, compilation, portability, link, version, and diff
  checks. Do not add a generic prose gate.
- **PR Fast:** Reproduce Linux model-free behavior, CLI dispatch, fixtures,
  portability, bundled UI, and site health on the exact PR commit.
- **PR Full:** Download pinned Docling models and validate complete
  model-dependent extraction and both committed corpus specifications through
  the existing corpus application path. Local/Fast checks separately validate
  literal CLI help and dispatch.
- **Main:** Validate the exact squash-merged commit through installed-runtime
  version/lifecycle smoke and confirm unchanged Pages health.
- **Release:** Verify the annotated tag target, non-draft/non-prerelease
  source-only GitHub Release, and downloaded generated archives containing
  0.8.1 metadata. Publish no custom assets.
- **Scheduled:** Add none. The repository has no scheduled workflow and this
  change introduces no need for one.

Evidence remains reusable only while the candidate text, commands, paths,
relevant implementation, fixtures, lockfile, guides, workflow definitions,
and model inputs remain unchanged. Squash merge changes commit identity, so
Main smoke remains distinct. Tag retargeting, release recreation, or archive
regeneration invalidates release evidence.

A false claim, broken command or link, version mismatch, dependency drift,
excluded change, CI failure, or review finding blocks acceptance. Missing
local models do not block model-free local validation, but PR Full must pass
complete model-backed coverage.
