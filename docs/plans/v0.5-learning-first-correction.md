# v0.5 Correction Plan — Learning-First Document Lifecycle

**Status:** Proposed for owner review and approval  
**Planning base:** clean `main` at `a500464554bd31b4c7569d50df577d00c6eb71bb`,
matching `origin/main`  
**Release state:** v0.5 release is paused; no tag or GitHub Release exists in
the locally verified repository state  
**Implementation authority:** none until the owner approves this exact frozen
plan and SHA-256  
**Target release:** `v0.5.0`, only after all correction PRs, review, CI,
retrospective, and separate release approval

## 1. Why this correction exists

The merged v0.5 implementation added a useful read-only local Workbench, but it
also introduced a compatibility and provenance system that does not match the
project.

The project is learning-first and source-only. It does not publish a hosted
API, stable third-party JSON contract, schema service, data service, or
prebuilt executable. Users can update the repository and regenerate current
records. The current code instead treats package version, Python version,
dependency versions, `uv.lock`, command IDs, and a provenance registry as
artifact compatibility identity.

That design caused unnecessary coupling:

- 25 JSON Schema files, including a shared `common-v0.5` schema;
- 12 artifact families that require `build_provenance`;
- runtime reads of the working tree's `uv.lock` and `pyproject.toml`;
- an append-only supported-provenance registry;
- versioned fixture paths;
- versioned internal Workbench HTTP payloads;
- 3,202 lines of unified-schema baseline tests;
- a 1,190-line schema/documentation audit tool;
- a 1,156-line central semantic-validation module;
- repeated compatibility checks across observation, diagnosis, refinement,
  corpus, verification, fixtures, and Workbench admission.

The correction removes that burden while preserving the domain evidence,
integrity checks, human-decision boundary, and local Workbench.

## 2. Product outcome

The project teaches and exposes one document lifecycle:

```text
raw business document
  -> format-aware extraction
  -> canonical DoclingDocument
  -> evidence-based diagnosis
  -> explicit human decision
  -> controlled refinement
  -> prepared document revision
```

The CLI and bundled local Webapp are two interfaces over the same application
and domain behavior.

- The CLI is precise, scriptable, and compact.
- The Webapp is visual and can become richer than the CLI.
- The current v0.5 Webapp remains read-only.
- The HTTP server is an internal loopback bridge for the bundled Webapp.
- No interface or data shape is promised to third parties across releases.

## 3. Boundaries

### In scope

- remove development/runtime provenance from workflow data;
- simplify current persisted record formats;
- simplify the four CLI verification results;
- simplify fixture registries and remove fixture release-version directories;
- simplify the Workbench's internal HTTP payloads;
- establish thin CLI and HTTP adapters over application services;
- rename the user command from `tcw` to `corpus`;
- rename `inspect-corpus` to `inspect`;
- make local setup, execution, and source-only distribution clear;
- replace the oversized v0.5 schema baseline and compatibility tests;
- reduce duplicated work inside CI jobs;
- rewrite current public and learning documentation to match the corrected
  product.

### Out of scope

- landing-page visual redesign;
- hosted visualization or remote access;
- Docker or Docker Compose delivery;
- prebuilt standalone executables;
- package-registry or container-registry publication;
- public Python API;
- public/stable HTTP API or JSON Schema contract;
- cross-version artifact readers, migrations, or compatibility fixtures;
- database, background jobs, discovery, upload, or filesystem watching;
- mutation through the v0.5 Webapp;
- chunking, embeddings, indexing, retrieval, generation, or RAG evaluation.

The source and raw extraction artifacts remain immutable. Diagnosis does not
authorize mutation. Interpretive refinement still requires explicit human
confirmation.

## 4. Settled technical decisions

### 4.1 Repository, runtime, and distribution

- The repository remains source-only.
- `pyproject.toml` and `uv.lock` describe the development/build environment,
  not workflow records.
- The supported development runtime is CPython 3.12. Declare it truthfully as
  `requires-python = ">=3.12,<3.13"` and set Ruff's target to `py312`.
- CI and reproducible setup use `uv sync --frozen --python 3.12`.
- Normal use after sync is `uv run corpus ...`, without `--frozen`.
- An activated `.venv` can run `corpus ...` directly.
- `python -m tiny_corpus_workbench ...` remains a developer fallback.
- `uv build` can remain a packaging sanity check. It is not a binary
  distribution promise.

Delete all runtime behavior that reads or hashes the current checkout's
`uv.lock` or `pyproject.toml`, compares installed dependency maps, or rejects a
command because package/build provenance differs.

### 4.2 User command system

Expose exactly this command system:

```text
corpus --version
corpus observe
corpus verify
corpus diagnose
corpus verify-diagnosis
corpus draft-refinement
corpus resolve-refinement
corpus verify-refinement
corpus inspect
corpus verify-corpus
corpus workbench
```

Do not retain a `tcw` alias or an `inspect-corpus` alias. Historical tags retain
the old interface.

`corpus --version` reports the project release version from installed package
metadata. The version is not copied into workflow records or API payloads.

### 4.3 Application and domain boundary

Create `src/tiny_corpus_workbench/application/` as an internal package with
use-case modules for:

- observation;
- diagnosis;
- refinement;
- corpus inspection;
- verification;
- Workbench queries.

Each correction slice moves only its relevant orchestration into this layer.
Do not perform a separate sweeping file-move refactor.

The CLI owns argument parsing, stdout/stderr rendering, and exit-code mapping.
The HTTP server owns loopback transport, request validation, response limits,
and headers. Neither adapter owns lifecycle rules.

Existing extraction adapters, diagnosis rules, revision mechanics, corpus
aggregation, record admission, and integrity helpers remain domain/internal
implementation. The application modules call them.

This package is internal. It does not create a stable public Python API.

### 4.4 Persisted workflow records

Persistence exists to make the lifecycle inspectable and to provide inputs for
later stages. It is not a compatibility promise.

The four generated record roots are:

| Record | Root manifest | Purpose |
|---|---|---|
| Observation | `manifest.json` | Source identity, extractor outcomes, canonical document, comparison, and actual extraction inputs |
| Diagnosis | `diagnosis-manifest.json` | Subject identity, ruleset, findings, evidence, and report |
| Refinement | `refinement-manifest.json` | Human decision, transformation, history, and optional prepared revision |
| Corpus | `corpus-manifest.json` | Explicit corpus execution, nested records, aggregate summary, and static report |

Every root manifest contains:

```json
{
  "record_type": "observation | diagnosis | refinement | corpus",
  "format_version": 1
}
```

`format_version` is an integer internal data-format marker. It is independent
for each record family even when all current values are `1`. Increment it only
when that family's current reader cannot understand the new shape.

Supporting files do not repeat `record_type`, `format_version`,
`schema_version`, or package version. A corpus specification and a refinement
decision are command-selected domain inputs, so their role is known from the
command and they also omit release/schema identity.

Readers accept only the current format for their record family. A missing or
unknown header produces a concise error that tells the user to regenerate the
record with the current project. Do not dispatch to old readers, migrate old
data, or silently overwrite/delete user data.

If a future release breaks a format, users can archive or delete generated
records and regenerate them. Human decision files can be archived separately
when their historical meaning matters.

### 4.5 Domain evidence that remains

Keep evidence that explains document preparation:

- source identity, media type, size, and hash;
- extractor name, installed extractor version, status, errors, duration, and
  produced artifact descriptors;
- Docling document schema name/version for the canonical document;
- extraction configuration;
- actual local model inventory when models participate in extraction;
- comparison metrics;
- ruleset identity and finding evidence;
- explicit decision, actor, note, and state;
- before/after hashes, reversible edits, lineage, and transformation history;
- corpus member inputs, outcomes, aggregates, nested record identities, and
  integrity descriptors.

Extractor versions are descriptive evidence. They are never compatibility
gates.

Remove:

- `build_provenance`;
- `provenance_id`;
- package/project version in records;
- Python implementation/version in records;
- `uv.lock` hash/path in records;
- jsonschema and general dependency maps in records;
- command/generator version identity;
- supported provenance tuples/registry;
- verifier/package version in verification output;
- package/runtime display in Workbench payloads.

Record IDs and hashes must be recomputed from domain inputs only. Package,
Python, lockfile, dependency, command, and generator identities must not affect
observation, diagnosis, draft, refinement, transformation, corpus, session, or
edge identity.

### 4.6 JSON Schema policy

JSON Schema remains an internal validation tool only where it is cheaper and
clearer than replacement.

Keep small, self-contained, unversioned internal schemas for:

- observation manifest and comparison;
- diagnosis manifest and finding set;
- refinement draft/decision, manifest, transformation, and history;
- corpus specification, manifest, and summary;
- the four verification result shapes.

Use symbolic internal catalog keys such as `observation-manifest`, not
`tcw.*` public/versioned identifiers. Schema filenames are unversioned.
Schemas do not depend on a shared common schema. Small primitive definitions
may be duplicated when that keeps each model understandable in isolation.

Move semantic invariants next to the relevant domain/application module.
Delete the central `semantic_validation.py` dispatch when all families have
migrated.

Delete JSON Schemas for:

- authored fixtures and fixture registries;
- supported provenance;
- Workbench startup, projection, record detail, and errors;
- `common-v0.5`.

Fixture generators use small Python validators and focused tests. Workbench
payloads use internal Python dataclasses/typed structures plus focused
serialization tests.

### 4.7 Verification output

The four verifier commands print command-specific JSON objects for users and
automation:

- observation verification;
- diagnosis verification;
- refinement verification;
- corpus verification.

They report integrity, relationship, derivation/replay, and advisory states
that are relevant to the inspected record. They contain no schema version,
runtime, package, verifier, dependency, or lock information.

Retain four drastically reduced internal JSON Schemas because pruning the
existing small schemas is cheaper than replacing all verification validation.
The verifier selects its schema in code; output does not announce the schema.

### 4.8 Fixtures

Use this current-tree layout:

```text
fixtures/authored/
fixtures/golden/
fixtures/diagnosis/
fixtures/refinement/
fixtures/corpus/
```

Remove the `v0.5` path component. Registries describe current fixture IDs,
paths, expected learning properties, hashes, and generator recipe where
useful. They contain no release/schema/runtime/build provenance.

Fixtures protect against unintended current behavior changes. Intentional
design changes update fixtures and expectations together. Git tags/history
preserve old fixture generations.

### 4.9 Workbench

Keep the v0.5 Workbench read-only and loopback-only.

Retain:

- explicit record roots only;
- no discovery, upload, workflow execution, or mutation;
- Host, Origin, and HTTP method enforcement;
- traversal and symlink protection;
- open-without-follow admission;
- captured-byte/frozen-view integrity;
- explicit artifact allowlists;
- relationship and containment checks;
- structured-response and artifact-size limits;
- safe DOM construction and existing security headers.

Change:

- API paths from `/api/v0.5/...` to internal `/api/...`;
- remove runtime/package/provenance/schema-version display;
- serialize only fields consumed by the bundled UI;
- represent projection, record summary/detail, relationship, artifact, and
  error objects with internal Python models;
- replace full versioned API-schema fixtures with focused payload and
  frontend-consumer tests.

The Workbench may later gain richer lifecycle interactions, but any future
mutation must call the same application services as the CLI and requires a
separate milestone.

## 5. Implementation sequence

PR 0 alone uses `milestone/v0.5-learning-first-correction`. Create that branch
from the approved base, use it only to establish the correction plan and
ledger, and open one normal PR to `main`. Its first checkpoint commit contains
only the exact owner-approved plan and the initial correction ledger. Only
after that checkpoint may later commits on the same branch update status,
roadmap, release-draft, tests, tools, and CI. Validate and independently review
the complete PR 0 delta, not only the first checkpoint. After its reviewed head
passes hosted CI, squash-merge it, wait for green post-merge `main` CI, and
delete the establishment branch.

Every later PR uses a fresh independent task branch created from the latest
green `main`. It targets `main`, is not stacked, and never depends on unmerged
work. Apply the plan-build-review builder, fresh independent reviewer, unchanged
reviewed-head validation, and checkpoint gates inside that one task branch.
Record the task base, validation, verdict, reviewed head, squash merge, and
post-merge `main` CI in the correction ledger. A later task does not start
until the prior task is merged and its post-merge `main` CI is green.

If a PR exceeds one coherent review question, split out a behavior-preserving
prerequisite. File count caused by mechanical fixture path or schema deletion
does not by itself require a split, but mixed unrelated behavior does.

During the sequence, a migrated record family has exactly one accepted current
format. All downstream readers, verifiers, corpus composition, and Workbench
admission for that family change in the same PR. Unmigrated record families
keep their existing shape until their own PR. This is a short-lived
implementation sequence, not a dual-format compatibility layer. Any temporary
Workbench serialization needed only for an unmigrated family is removed in
PR 5.

The task branch may contain temporary controlled failure-probe commits, but the
final reviewed head must contain no probe and must pass every required gate.
Do not change a reviewed head after `PASS`; if it changes, rerun fresh review.

head. Before final review, the task branch records its base, status
`reviewing`, focused/full validation, and the implementation checkpoint being
reviewed; verdict, squash, and post-merge fields remain `pending`. After squash
and green post-merge `main` CI, the next task branch first records the prior
task's `PASS`, reviewed checkpoint, squash SHA, and main-CI evidence, then
records its own task evidence. The reviewer checks that bookkeeping together
with the new task. PR 9's squash and post-merge evidence is recorded during the
separately authorized retrospective/release-documentation step; it cannot be
pre-claimed in PR 9. Empty future fields use the literal `pending`, never an
invented SHA, verdict, or run.

## 6. Test strategy

Tests protect domain behavior, not historical implementation accidents.

### Keep and focus

- canonical JSON/hash behavior where identity is meaningful;
- source immutability and atomic publication;
- extractor result separation and model evidence;
- diagnosis rule determinism and concrete evidence;
- explicit approval/rejection boundary;
- reversible refinement and lineage;
- corpus completeness, partial execution, and static report safety;
- artifact tamper detection;
- Workbench record admission, frozen bytes, relationship states, path safety,
  HTTP authority, response limits, and safe frontend rendering;
- CLI stdout/stderr and exit-code behavior;
- one current-format unknown-version rejection;
- one clean-export lifecycle/Workbench smoke test;
- real offline extractor coverage in the full job.

### Remove

- exact old Git commit, branch, tag, or repository-history expectations;
- old schema readers and cross-version artifact matrices;
- append-only provenance registry tests;
- dependency/lock/Python/package equality tests inside workflow behavior;
- full JSON Schema placement/evidence inventories;
- full Workbench API schema baselines;
- tests whose only purpose is to preserve `/v0.5` names or versioned fixture
  directories;
- document-policy tests that invoke Git, pin a commit/tag/base, hash or
  fingerprint whole historical files, compare historical bodies, or encode a
  repository snapshot;
- duplicate execution of model-free suites in both CI jobs.

Deleting oversized tests does not reduce protection if focused behavior tests
cover the actual domain and security invariants listed above.

## 7. Review and merge protocol

For every PR:

1. Use the establishment branch only for PR 0. For PR 1 onward, create one
   fresh task branch from the latest green `main`; do not reuse, stack, or base
   it on another task branch.
2. Record the exact base and task status in the ledger. State the single review
   question, owned contracts, exclusions, and intentionally deleted
   guarantees.
3. Give a fresh builder only that task packet. Run its focused commands,
   negative probes, complete slice gate, and clean/diff checks.
4. Freeze the implementation checkpoint and give its exact base/head and
   evidence to a fresh independent reviewer. `PASS` applies only to that
   unchanged reviewed delta.
5. If review finds an issue, return to `building`, fix it on the same branch,
   rerun every affected gate, and obtain a new fresh review. Do not retain an
   earlier verdict after the head changes.
6. Record pre-merge evidence using the ledger protocol in Section 5, then open
   or update one normal PR targeting `main`. Never create a temporary stacked
   review PR.
7. Triage hosted comments against the approved scope. Any accepted correction
   changes the reviewed head and therefore requires refreshed validation and
   fresh independent review.
8. Require green hosted checks on the final reviewed head, then squash merge.
9. Require green post-merge `main` CI, record it through the next-task ledger
   update, and delete the task branch before starting the next task.
10. If main regresses, stop the sequence and repair or revert before
    continuing.

No PR may intentionally leave `main` broken. Do not close/abandon a failed PR
and merge a separate repair after a known regression. Fix before merge, or
revert the merged squash if a post-merge-only problem appears.

If a behavior-preserving prerequisite becomes necessary beyond the packets in
this plan, stop and obtain owner approval for the amended task/PR sequence
before creating that branch. A split never authorizes stacked work or a second
unmerged dependency.
