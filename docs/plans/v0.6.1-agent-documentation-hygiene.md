# v0.6.1 — Agent Documentation Hygiene

**Base:** `main == origin/main == efe6210c3dc18f98f595ba2f0a6d17f97c316ee5`
**Target:** `v0.6.1`, source-only maintenance
**Role:** durable outcome, rationale, scope, and acceptance record; never a
task ledger or execution-evidence log

## Outcome and rationale

Reduce the context a future agent must read before useful work. Keep final
outcomes, design rationale, boundaries, concise validation outcomes, and later
direction. Remove completed execution bookkeeping already preserved by Git and
GitHub.

The repository will have a concise navigation-only `CURRENT.md`, one
recognizable outcome-and-rationale record per completed plan, one consolidated
v0.5 record, no tracked ledger or obsolete correction/amendment document, and
aligned v0.6.1 source-release metadata. This changes documentation ownership,
not the learning product.

## Decisions

### Owner-set

- Completed plan records have similar responsibility, not a rigid template:
  final outcome, rationale, boundaries, concise validation outcome, and later
  direction only.
- `CURRENT.md` is an unambiguous agent index, not a changelog, archive, or
  ledger.
- The original, correction, and lasting amendment decisions for v0.5 become
  one final record without problem or clarification chronology.
- Obsolete execution documents and all historical ledgers are removed. Git and
  GitHub remain the detailed execution-history authorities.
- Product behavior, records, schemas, fixtures, learning exercises, Workbench,
  landing page, CI responsibility, deployment, compatibility, security, and
  roadmap direction do not change; the source `__version__` constant changes
  only to align release identity.
- Delivery uses one semantic task, one task review, one integration review, one
  PR, and controlled release. Native task state is the only lightweight ledger.
- A fresh exact-plan review must return `PASS` with zero findings, then the
  owner must approve its SHA-256. The approved bytes are saved and committed
  before implementation, remain immutable, and never receive task state or
  evidence.

### Inferred

- Save these exact approved bytes first as
  `docs/plans/v0.6.1-agent-documentation-hygiene.md` on the implementation
  branch. The plan commit and T1 share the single PR; there is no establishment
  or closeout PR.
- Keep `CURRENT.md` release-neutral: it may state source/package version
  `0.6.1`, but GitHub Releases owns published-release state. Keep the README
  milestone table unchanged; its patch releases are intentionally omitted.
  The release note may use durable wording and its canonical tag link without
  claiming publication before it exists.
- Regenerate the lock, but accept only the root project version change. Change
  a test only if it contains a removed path literal. Remove only the obsolete
  deleted-plan rule from `.gitattributes`.
- Use one-time, change-specific review and link checks. Add no generic prose,
  Markdown, or historical-evidence validator.

A different file boundary, second PR, tracked ledger, or product-facing change
requires a new owner decision.

## v0.5 consolidation contract

The single v0.5 record preserves the final rationale and boundary for:

- source and extraction immutability, diagnosis without mutation authority, and
  explicit human control of interpretive refinement;
- four persisted record families and their self-contained schema
  responsibilities;
- dependency-free frozen Python values for transient verification results,
  without verification-result schemas;
- canonical proposal-only drafts and
  `refinement-manifest.json.decision` as the only persisted decision authority;
- final golden, diagnosis, refinement, corpus, and test fixture roles;
- `corpus` as the only lifecycle CLI, with execution and mutation outside the
  browser;
- framework-neutral application services shared by CLI and Workbench;
- bundled read-only, loopback-only Workbench and lightweight internal payloads,
  with no public or stable API promise;
- trusted-local integrity limits and source-only distribution;
- focused CI responsibilities without executable documentation policy.

It explains the accepted design for learners. It omits correction phases,
amendments, task IDs, branches, PRs, commits, reviewers, run IDs, candidate
hashes, and clarification chronology.

## Review, delivery, and stage validation

1. **Plan gate:** fresh exact-plan `PASS` with zero findings, then exact-hash
   owner approval. Any byte change restarts this gate.
2. **One branch:** commit the approved plan bytes before T1. This commit is
   inside the single PR, not a separate establishment.
3. **Task review:** after T1 and local validation, a fresh reviewer checks the
   T1 diff and criteria; require `PASS` with zero findings.
4. **Integration review:** a fresh reviewer checks the complete base-to-head
   candidate for plan immutability, ownership, deletion/link consistency,
   version alignment, and scope; require `PASS` with zero findings.
5. **One PR:** open the complete ready-for-review candidate. Evaluate each
   substantive comment and require Fast and Full. They cover the exact locked
   Linux candidate: unit/model-free behavior and existing assets, site,
   fixtures, portability, and model-dependent extraction. Refresh affected
   review/check results after any change; squash-merge only the accepted head.
6. **Main:** at the merge SHA, require Main smoke for installed version and the
   model-free lifecycle, plus Pages build/deploy for the unchanged site.
7. **Release:** run fresh exact-SHA readiness review and obtain owner
   authorization. Create annotated `v0.6.1`; publish it latest, non-draft,
   non-prerelease, source-only, without custom assets. Verify tag peel, Release
   metadata, the release note's now-live canonical link, and a downloaded
   archive containing the immutable plan, release note, and `0.6.1` metadata.
   Dispatch existing CI at the tag and require Fast and Full. GitHub Releases
   records publication; do not edit CURRENT or README afterward.
8. **Close:** end with clean `main == origin/main`, no active work, no plan
   mutation, and no closeout PR.

There is no scheduled workflow and none is added. PR Fast/Full plus explicit
tag-ref Fast/Full provide equivalent exact-source coverage; this documentation
patch has no hosted runtime or time-varying integration needing periodic checks.

## Failure modes and prerequisites

- If condensation loses a lasting decision, restore it in the correct retained
  owner rather than retaining a second authority.
- If a removed path remains live or a required edit falls outside scope, repair
  it within the stated boundary or stop for owner direction.
- If history conflicts with current behavior, retain accepted historical
  rationale and point exact current truth to its current owner; do not redesign.
- Reject dependency drift. Stop for re-review and owner decision if the frozen
  plan, excluded surfaces, roadmap, CI responsibility, or any public,
  compatibility, deployment, or security posture would change.
- Any candidate change refreshes affected review and validation results.
