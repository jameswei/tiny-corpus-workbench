## 1. Plan authority

The design source contains the owner-reviewed v0.9 decisions and is the scope
ceiling for this plan. After a zero-finding review and explicit approval, this
exact plan becomes the implementation contract.

Planning, building, and review must obey these rules:

1. Every product behavior must trace to an accepted design-source section.
2. Repository inspection may select the smallest implementation mechanism. It
   may not invent a capability, status model, compatibility promise, or
   generalized data model.
3. If current code or data exposes a product case not decided here, stop and ask
   the owner. Do not infer a design.
4. Preserve the existing application services, verification, admission,
   immutable records, action-token model, upload limit, and local internal HTTP
   boundary unless this plan explicitly changes their presentation or wiring.
5. Do not add a generic lifecycle graph, branching model, missing-relationship
   UI, or new user-facing relationship classification. Existing admission and
   projection verification continue to accept or reject a complete workspace
   snapshot.

## 2. Outcome and boundary

Release `v0.9.0` as a substantial redesign of the bundled Workbench UI/UX. A
learner selects one source document, follows a focused
Observe → Diagnose → Refine → Revision journey, and opens supporting evidence
without navigating a flat record dashboard or one expanding page.

The owner-derived requirements are the behaviors in section 3. The minimal
implementation inferences are internal projection regrouping, internal metadata
transport, a catalog localizer, and shared comparison/reader components. They
create no new public API, schema, deployment/security model, or compatibility
promise. In the roadmap, v0.9 is redesign and polish after functional v0.8.1;
it does not consume the v1.0 outcome.

In scope:

- the accepted desktop and narrow-screen shell, navigation, stages, inspectors,
  comparisons, readers, recovery states, and learner explanations;
- English and Simplified Chinese Workbench UI localization;
- a canonical rule reference;
- the smallest internal projection/HTTP changes needed by the accepted UI;
- tests, learning material, public documentation, and v0.9 release metadata.

Out of scope:

- new rules, refiners, producers, persisted schemas, migrations, or CLI behavior;
- re-observation, arbitrary branching, automatic repair, or browser corpus
  execution;
- a resumable pending-proposal snapshot or lifecycle/DOM session state (the
  locale preference is the sole browser-local exception), filesystem watching,
  background workspace polling, or automatic mutation replay;
- cross-version workspace readers, migrations, or compatibility handling;
- rendering or serving uploaded originals;
- a frontend framework, asset build pipeline, remote dependency, or public API.

## 3. Accepted Workbench behavior

### 3.1 Shell and navigation

- Use the accepted candidate-A composition: stable-width Documents/Corpora
  sidebar, learner-question stage stepper, one central work surface, and a
  stage-scoped `Summary | Evidence | Artifacts` inspector.
- Open large comparisons and readers on the central surface. Do not restore the
  separate lineage navigation.
- Header: `Corpus Workbench`, package-metadata version, `?` Rule reference,
  and one direct EN/中 toggle. Remove repeated identity text and
  `Local workspace · Ready`.
- Footer: matching rounded treatment, centered project credit and
  `GitHub Repository` link, with no visible raw URL.
- Keep the outer desktop surface visually stable in short states without
  stretching inner cards. Let long content grow the page. Reflow naturally on
  narrow screens.

### 3.2 Sidebar, Add, ordering, refresh, and notifications

- Use one Workspace toolbar with a compact Refresh icon, then simultaneously
  visible Documents and Corpora sections. Documents owns a compact Add icon;
  Corpora is read-only. Use one card shell. Corpus metadata is
  `Verified · N members`; findings belong inside corpus inspection.
- One sidebar document represents one source across immutable revisions. Use a
  fixed width and at most two filename lines. Show the full selected name in the
  central context; hover/focus may also reveal it.
- Empty-state Add and the sidebar Add icon open one modal with exactly:
  `whitespace-cleanup.md` complete preparation, `policy-memo.md` no-findings
  inspection, and one `.docx`/`.md`/`.pdf`/`.txt` upload up to 32 MiB.
- A new source is selected and Observe starts immediately. Identity is content
  SHA-256 plus media type. A repeated guided source or unchanged upload
  reactivates its document, publishes no Observation, and explains the result.
  Do not add `Observe again`.
- v0.9 is a clean break: pre-v0.9 releases have no external users or user data
  requiring compatibility. Accept one Observation root per source identity. If
  a development-era workspace contains more than one, reject the complete
  candidate through the accepted workspace-load failure, leave every file
  unchanged, and direct the learner to a new or clean workspace. Do not migrate,
  merge, hide, or model old roots.
- Sort by first Observation time, newest first, with deterministic source
  identity as tie-breaker. Later records, selection, and reactivation do not
  reorder a document. Apply the same rule to CLI records found by Refresh.
- Workbench actions refresh their own results. Explicit Refresh alone discovers
  external CLI changes; it runs no producer, preserves selection/stage, and
  retains the last accepted snapshot on failure. No watcher or periodic poll.
- Global feedback uses one lower-right non-layout toast. Success/info dismisses
  after about four seconds, pauses on hover/focus, and has Close. Failure stays
  until dismissed or replaced by success. Use polite/assertive announcements.
  Keep lifecycle outcome banners as durable stage content.

### 3.3 Document lifecycle

- Observe is shared by the source. Repeat only
  Diagnose → Refine → Revision as numbered preparation rounds.
- Show compact `Preparation round n of N` / `Starts from Revision n` context,
  then the stepper and stage cards at one 12 px vertical rhythm.
- Revision shows `Original → Revision 1 → Revision 2` and marks the latest
  current. Historical revisions are inspectable and read-only. Only the latest
  revision can start another round.

Observe:

- Group filename, media type, size, and SHA-256 as one source object.
- Show real observation stages, extraction/canonical evidence, and a clear
  Diagnosis handoff.
- For uploads, show metadata and explain why the original is not displayed.
  Never render or serve its content.

Diagnosis:

- Explain that deterministic diagnosis is read-only. Keep the learner on the
  focused stage while it runs.
- Lead with document meaning and finding count. A green banner means Diagnosis
  completed; it does not encode severity.
- Each finding uses its canonical INFO/WARNING/ERROR severity; D009 is INFO.
  Show name first and ID second. Explain why it matters and place the action in
  an `Available next step` area.
- State that a finding is evidence, not an invalidity or compliance verdict.
- For `NO_FINDINGS`, say that no fixed rule matched and no content changed.
  Never say Valid or Passed. Keep Refine and Revision clickable as
  `Not needed` explanations, and keep Diagnosis evidence available.

Refine:

- Show finding and supported refiner before proposal creation; explain that a
  proposal does not change the document.
- Keep proposal creation and its running state on the same surface, then replace
  them with a learner-readable comparison. Hide internal target JSON.
- D009 uses visible whitespace; D009/D010 text changes and D007 structural
  movement use one shared comparison component. Support bounded preview,
  inline open/close full view, responsive side-by-side/stacked layout, long text,
  multiple edits, and compact accessible `← n of N →` navigation.
- Put equally weighted Approve and Reject icon choices in action guidance. Show
  selection and enable a separate primary `Record decision` only after choice.
- Stay on the Refine outcome after submission. Approval offers
  `View prepared revision`. Rejection is a completed decision: base unchanged,
  no revision, evidence retained, Revision clickable as `Not needed`.

Revision:

- Lead with `Prepared revision created`. Explain the preserved base, immutable
  successor, approved edit, and forward/inverse evidence.
- Reuse the same comparison component in applied mode. Keep finding/refiner
  secondary; link prepared-document and history artifacts from the inspector.
- Use `Optional next step` to explain that the revision may start another
  Diagnose → Refine → Revision round without forcing it.

### 3.4 Inspector, artifacts, corpus, and hashes

- Keep summaries primary and audit detail in the inspector. Selecting a corpus
  hides the document stepper and uses the same inspector composition.
- At a published Observation, Diagnosis, or Refinement, Evidence may include one
  low-emphasis note pointing to `corpus --help` and `learning/`. Remove
  generated commands and argument/path cards. Show no CLI note for a pending
  proposal.
- Pretty-print JSON. Show Markdown as literal source. Show verified
  project-generated HTML in a sandbox with no scripts, network, external
  resources, navigation, and offer formatted source mode.
- Comparisons use the shared comparison component. Other readers are full-width,
  show artifact role/media type/size/hash, explain oversized content without
  truncation, and return to the same selection/stage when closed.
- Reader controls are compact localized icons for close, wrap, copy, and HTML
  source mode, with visible focus, tooltips, accessible names, and
  `aria-pressed` for toggles. Source backgrounds match their enclosing surface;
  source text uses a slightly smaller monospaced font.
- Backend models, payloads, identity checks, records, artifacts, and copy use the
  full 64-character SHA-256. Visible Workbench hashes use one shared monospaced
  `first 10…last 8` renderer with the full value in the native hover title.

### 3.5 Localization and Rule reference

- Localize Workbench-owned UI only: chrome, stages, actions, guidance, known
  errors, tooltips, accessible names, and announcements.
- Never translate filenames, document/artifact content, hashes, stable IDs,
  schemas, records, or payloads. Unknown rule/refiner names use source values.
- First visit uses browser language with English fallback. Persist an explicit
  choice in `localStorage`. Switching does not reload or reset selection,
  stage, inspector tab, proposal, or revision; update DOM `lang` too.
- Use one catalog-backed localizer, identical EN/zh-CN key sets, stable internal
  keys, and native `Intl`. Do not scatter bilingual literals. The toggle shows
  its target locale. A third locale and menu are outside v0.9.
- Map known error codes to localized guidance while preserving arbitrary backend
  error evidence as data rather than translating it.
- The `?` button opens a dismissible true modal and makes the background inert.
  Show D001–D010 with ID, localized learner name, canonical severity, and one
  concise condition explanation. Ordinary intro text explains that a finding is
  evidence, not verdict or change authority. Show refiners for D007/D009/D010.
- Derive rule membership, IDs, versions, severities, parameters, and D-to-R
  mappings from Python `CURRENT_RULES` and the refiner registry. Frontend
  catalogs contain localized copy keyed by canonical IDs, never a second
  ruleset or mapping.

### 3.6 Failure, reload, and restart

- Distinguish a valid empty workspace from initial verification failure. Failure
  shows durable `Workspace could not be loaded`, says no partial state was
  accepted and no files changed, keeps Refresh, and disables Add/mutations. Do
  not duplicate this central state with a persistent toast.
- A confirmed pre-publication failure stays in the stage, says no record exists
  and source is unchanged, and leaves later stages clickable as `Unavailable`.
  Offer Retry only when the server confirms publication did not occur.
- If publication succeeded but refresh failed, retain the last accepted view and
  offer Refresh; never rerun the producer.
- For an unknown mutation outcome, reconcile the workspace before re-enabling
  the action. Never replay a mutation automatically.
- Preserve the current private canonical draft-file mechanics, but do not make a
  pending proposal UI, selection, or decision authority resumable. Browser
  reload or server restart returns to the latest published record; recreate the
  deterministic proposal without rerunning Observe/Diagnose. Restore decisions
  only from immutable Refinement records, never from draft or DOM state.

### 3.7 Bounded temporal invariants

Preserve only these existing or owner-accepted time-sensitive behaviors:

| Scenario | Invariant and learner-visible result |
| --- | --- |
| Observation polling | Poll only while the job is queued/running; stop after a terminal snapshot. A skipped fast stage may appear completed but is never claimed as observed live. |
| Mutation ownership | Observation and lifecycle mutation never overlap. A second observation or lifecycle request gets the existing busy result while observation owns the lease. |
| Sequential lifecycle HTTP | While a synchronous lifecycle request runs, later routed requests wait and then observe post-release state; do not add concurrent dispatch. |
| Navigation and submission | Disable record navigation and repeat submission while the lifecycle mutation is unresolved. After the confirmed outcome, re-enable navigation and unrelated eligible actions; remove or permanently disable that completed proposal's decision controls. |
| Stale action token | Refresh the token and require a new explicit click; never replay the rejected mutation. |
| Refresh/reconciliation | Preserve the last complete snapshot on refresh failure; after an unknown mutation outcome, reconcile before enabling another mutation. |
| Shutdown | Stop new observation acceptance and wait for accepted observation/publication work or the active synchronous request to reach its existing terminal boundary. |

Focused tests must exercise consumer-visible ordering, terminal stopping,
mutual exclusion/waiting, no replay, snapshot preservation, and shutdown. This
matrix does not introduce job history, cancellation, concurrency, or new states.

## 4. Implementation checkpoints

These are checkpoints in one atomic v0.9 feature PR, not separate PRs or
independent designs.

## 5. Verification and acceptance

Run focused tests after each checkpoint. Before review, run:

```text
node --version
uv run --frozen --group test python -m unittest discover -s tests/unit -v
uv run --frozen --group test python -m unittest -v \
  tests.integration.test_v05_workflows \
  tests.integration.test_workbench_integration \
  tests.integration.test_workbench_observation_journey \
  tests.integration.test_workbench_lifecycle_journey
uv run --frozen python tools/validate_workbench_assets.py \
  src/tiny_corpus_workbench/workbench_assets
uv run --frozen python tools/validate_site.py site
uv run --frozen --group test python -m compileall -q src tests tools
git diff --check
```

Local cumulative and PR Fast require Node.js 24.18.1, matching CI. The
`node --version` prerequisite must fail the gate when Node is absent; required
DOM tests must not pass by skipping. Node remains test-only, not a Workbench
runtime or asset-build dependency. Keep DOM tests bounded to learner-observable
behavior. Do not encode prose, repository history, or implementation trivia as
policy tests.

Validation consumers and purposes:

| Gate | Distinct purpose |
| --- | --- |
| Local focused | Fast task feedback for the changed consumer and checkpoint. |
| Local cumulative | Complete unit/model-free integration, validators, and the human actual-browser journeys before PR publication. |
| PR Fast | Reproduce unit, model-free integration, assets/site, portability, and diff hygiene on GitHub's synthetic merge candidate. |
| PR Full extraction | Exercise model-dependent extraction behavior that the redesigned UI still consumes; it is not a second UI review. |
| Main smoke | Verify the exact merged, installed runtime and one whitespace lifecycle; do not repeat the PR suite. |
| Pages | Validate and deploy only the changed static public site artifact. |
| Release | Verify tag target, version metadata, release note, approved-plan snapshot, source archive, and published site link. |
| Scheduled | None; this source-only local tool has no time-varying external contract requiring one. |

Reuse evidence only when commit, command/workflow, inputs, runtime/browser
conditions, and supported claim are unchanged. A material code/config/input
change invalidates the affected evidence, not unrelated results. The numbered
journeys below are human actual-browser review; automation supplies supporting
behavioral evidence but does not replace visual/interaction judgment.

Required browser journeys at desktop and narrow widths:

1. empty → whitespace guide → D009 → proposal → approve → Revision/comparison;
2. the same path through rejection, with no Revision publication;
3. policy memo → `NO_FINDINGS` and readable Not-needed stages;
4. supported upload → grouped metadata/artifacts, never original rendering;
5. duplicate guided/upload identity → reactivation, no new record;
6. approved revision → second preparation round → history/read-only prior round;
7. corpus selection → no document stepper → shared inspector composition;
8. Refresh success/no-change/failure with stable selection and snapshot;
9. prepublication failure, publication-plus-refresh failure, and unknown
   mutation outcome, with no automatic replay;
10. reload/restart with pending proposal and completed decision;
11. EN/zh-CN switching across stages, modal, viewers, errors, tooltips,
    accessible names, and announcements without state loss;
12. Rule reference, JSON/Markdown/HTML readers, shared comparisons, oversized
    artifacts, copy, compact hashes, keyboard navigation, focus return, and
    reduced motion.

Review must fail if implementation adds unspecified states/branches, duplicates
the canonical ruleset/mapping, changes persisted schemas or CLI/decision
semantics, renders an uploaded original, adds remote/build UI dependencies,
copies comparison logic, scatters translations, foregrounds raw payload fields,
or requires CLI commands to finish a Workbench lifecycle.
