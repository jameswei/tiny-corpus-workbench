# v0.5.0 — Local Visual Workbench (Unreleased Draft)

**Status:** Unreleased. Implementation and technical integration are complete.
Release-readiness review and exact-SHA owner authorization remain required.

This draft describes the intended v0.5 learning outcome. It is not a release
announcement or a compatibility promise.

## Highlights

- Inspect explicit observation, diagnosis, refinement, and corpus records in a
  local browser.
- Explore a frozen in-memory projection without record discovery or session
  persistence.
- Use a bounded internal loopback bridge and authorized plain-text artifact
  responses.
- Keep workflow execution and mutation in the existing CLI.
- Preserve source immutability, diagnosis authority limits, refinement
  decisions, lineage, forward derivation, and exact reversal.

The interface uses bundled HTML, CSS, and JavaScript. It needs no remote
runtime resource. The server binds only to `127.0.0.1`, accepts only `GET` and
`HEAD`, and serves admitted artifact bytes from its startup capture.

## Current record policy

The four verifier outputs are dependency-free frozen Python dataclasses
internally and deterministic compact JSON on standard output.
There are no verification-result JSON Schemas.

The 11 retained self-contained JSON Schemas cover persisted and input
artifacts. Each Schema uses local `$defs` and has no cross-file reference.

`draft-refinement` emits canonical proposal-only `proposal.json`.
Inspect this file, but do not edit it.
`resolve-refinement` requires exactly one of `--approve` or `--reject`, together with the diagnosis and base.
The manifest decision is the only persisted structured authority.
There is no actor, note, manifest status, or `decision.json`.

An approved refinement contains its proposal and report plus transformation,
history, and prepared-document artifacts. A rejected refinement contains its
proposal and report but no prepared revision.
The report is derived from the manifest decision and is not decision authority.

Corpus admission accepts only fully verified approved revisions.
The Workbench is a read-only local internal bridge and derives its views from admitted records.

The project keeps one current format for each generated record family.
It provides no migration or cross-version reader.
Earlier Git tags preserve historical implementations.

The Workbench HTTP server is an internal bridge for the bundled interface. It
is not a public or stable API.

The repository is source-only. v0.5 does not promise prebuilt binaries,
Docker images, package- or container-registry delivery, or a hosted API.

## One-time setup

```bash
uv sync --frozen --python 3.12
```

Activate `.venv` to use `corpus` directly. You can instead prefix a usage
command with `uv run`.

## Start locally

```bash
corpus observe fixtures/golden/policy-memo.md \
  --output-root /tmp/corpus-workbench-observations
corpus workbench OBSERVATION_DIRECTORY --no-open
```

Open the printed URL. Stop the server with `Ctrl-C`.

Read the [Local Visual Workbench guide](../local-visual-workbench.md) for record
admission, browser views, API routes, security behavior, and integrity limits.

These commands describe the current source checkout. v0.5 remains unreleased.
