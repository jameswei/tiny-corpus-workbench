# Web Observation Workflow

Suggested time: 20–30 minutes.

## Learning goals

After this lesson, you can:

- run the guided observation in a browser;
- upload one supported document;
- follow real observation stages;
- inspect both extraction views;
- explain which state stays in memory and which evidence stays on disk.

## Terms

An **input** is the source accepted for one observation.

A **job** is the latest in-memory Web observation task.

A **record** is immutable evidence published by the observation service.

## Before you start

Run this setup from a clean source checkout:

```bash
uv sync --frozen --python 3.12
```

Activate `.venv` to use `corpus` directly:

```bash
source .venv/bin/activate
```

The guided example and Markdown upload do not need Docling model files.

## Exercise

1. Create an isolated workspace.

   ```bash
   LESSON_WORKSPACE="$(mktemp -d /tmp/tcw-v07-lesson.XXXXXX)"
   printf '%s\n' "$LESSON_WORKSPACE"
   ```

2. Start the Workbench.

   ```bash
   corpus workbench --workspace "$LESSON_WORKSPACE" --no-open
   ```

3. Open the printed URL in your browser.

   The Workbench shows an empty record list and the observation controls.

4. Select **Observe policy memo**.

   The browser lists each real stage and marks the current server snapshot. It
   does not show percentage progress.

5. Wait for the job to complete.

   The Workbench refreshes the workspace and selects the new observation.

   A fast stage can finish between browser polls. The list then marks it as
   completed without claiming that the browser observed it live.

6. Inspect the Docling and MarkItDown results.

   Retrieve a plain-text artifact only when you want to read its content.

7. Select `fixtures/golden/meeting-minutes.md` in the upload control.

8. Select **Observe selected file**.

   The browser shows source metadata. It does not show the uploaded original.

9. Wait for the second observation to complete.

   The record list now contains both immutable observation runs.

10. Stop the Workbench with `Ctrl-C`.

The Workbench stores the uploaded input under `inputs/` in the selected
workspace. It uses the input SHA-256 and original filename in that path.

The server keeps only the latest job in memory. A server restart clears the
job. It does not remove accepted inputs or published observations.

## Check your understanding

1. Why does the guided input not appear under `inputs/`?
2. Why can two observations of the same bytes produce two records?
3. What does a completed job say about record publication?
4. What happens when publication succeeds but workspace refresh fails?
5. Why does loopback binding not provide access control?

## Summary

The browser can run one guided or uploaded observation at a time.

The shared observation service publishes immutable evidence. The browser then
refreshes the complete workspace and selects the new record.

The browser shows source metadata but does not serve the uploaded original.
Diagnosis, refinement, and corpus workflows remain CLI operations.

Read the [Local Visual Workbench guide](../docs/local-visual-workbench.md) for
the complete workflow, workspace, integrity, and security behavior.
