# Corpus Inspection and Comparison

## Learning goals

After this lesson, you can:

- explain an explicit corpus specification
- run the golden and quality corpora offline
- find grouped evidence in the static report
- explain why a finding does not authorize a change
- add one existing verified revision to a temporary specification
- verify a corpus artifact and inspect live-input states
- perform a safe tamper experiment

Suggested time: 60–75 minutes.

## Before you start

Use CPython 3.12. Install the locked environment:

```bash
uv sync --frozen --python 3.12
```

Download the pinned PDF models before you go offline:

```bash
uv run docling-tools models download layout tableformer \
  --output-dir .cache/docling/models
```

Run each command from the repository root.

## 1. Understand the two corpora

Open these files:

- `fixtures/corpus/golden-matrix.json`
- `fixtures/corpus/quality-corpus.json`

The golden matrix has 12 members. It has three document families. Each family
has PDF, DOCX, Markdown, and text.

The quality corpus has five members. It uses existing diagnosis and refinement
sources. It covers D002, D003, D004, D005, D007, D009, and D010.

Each member declares one path. The command does not search a directory. It does
not accept a URL, stdin, or a glob.

Check both specifications:

```bash
uv run --frozen python tools/verify_corpus_specs.py
```

The checker reads the files. It does not rewrite them.

## 2. Run the golden matrix

Run the corpus:

```bash
uv run corpus inspect \
  fixtures/corpus/golden-matrix.json
```

The command prints one JSON line. Copy the directory that contains the printed
manifest path. This directory is `CORPUS_DIRECTORY`.

The status must be `COMPLETE`. The member count must be 12.

Open:

```text
CORPUS_DIRECTORY/report/index.html
```

Use the family-by-format matrix. Confirm that each family has four formats.

The exact finding result is:

- nine D009 findings
- D009 occurs only in the three TXT members
- no D010 finding
- no finding from another rule

The TXT fixtures use repeated spaces to align table columns. D009 reports this
mechanical condition. It does not decide that normalization is correct.

## 3. Inspect extractor comparisons

Go to **Extractor comparisons** in the report.

exact numeric deltas. It does not rank an extractor.

Follow these local links:

- Docling JSON
- Docling Markdown
- MarkItDown Markdown

## 5. Understand explicit revision inclusion

Corpus inspection never creates a revision. It can read one existing approved
revision.

A member can contain:

```json
"revisions": [
  {
    "refinement": "path/to/refinement",
    "diagnosis": "path/to/diagnosis",
    "base": "path/to/base"
  }
]
```

The three paths form one verification bundle. The refinement manifest decision
must be `APPROVED`, its revision ID must be non-null, its approved inventory
must be exact, and all verification states must match. A rejected refinement
is never a revision input. Persisted corpus JSON does not copy the decision.

Use the v0.3 lesson to create one D009 revision. Copy the quality specification
to a temporary directory. Use explicit paths in the copy. Add the verified
bundle to the `whitespace-cleanup` member.

Run `corpus inspect` with the temporary specification. Open **Revision and
transformation history**.

Confirm these fields:

- finding rule
- refiner ID
- parent identity
- chain length
- affected-reference count
- before and after hashes

Follow the proposal and history links. The report does not apply another
change.

## 6. Verify the corpus artifact

Run self-contained verification:

```bash
uv run corpus verify-corpus CORPUS_DIRECTORY
```

`artifact_integrity` must be `VERIFIED`.

`corpus inspect` performs this check in its private staging directory. It
publishes the directory only after the check passes. An unsafe symbolic-link
path stops publication and exits `5`.

Now compare live inputs:

```bash
uv run corpus verify-corpus CORPUS_DIRECTORY \
  --spec fixtures/corpus/golden-matrix.json
```

The specification, source, and model states must be `MATCH`.

These states are advisory. A later source or model change does not rewrite the
historical corpus artifact.

## 7. Test missing PDF models

Use a new output root and a missing model directory:

```bash
uv run corpus inspect \
  fixtures/corpus/golden-matrix.json \
  --output-root build/corpus-without-models \
  --docling-artifacts build/missing-models
```

The command exits `3` and publishes a `PARTIAL` report. The nine non-PDF
members complete. The three PDF members record model failures. No network
download starts.

## 8. Perform a safe tamper experiment

Copy one complete corpus directory. Keep the corpus run-ID directory name:

```bash
mkdir -p build/corpus-tamper-copy
cp -R CORPUS_DIRECTORY build/corpus-tamper-copy/
```

Edit this file in the copy:

```text
build/corpus-tamper-copy/CORPUS_RUN_ID/report/index.html
```

Verify the copy:

```bash
uv run corpus verify-corpus \
  build/corpus-tamper-copy/CORPUS_RUN_ID
```

The verifier must report an integrity failure and exit `5`.

Do not edit the original corpus directory.

## Knowledge check

1. Why must a specification list each source?
2. Why does MarkItDown never create a finding?
3. Why are the golden TXT D009 findings not approvals?
4. Why can a missing PDF model produce a partial report?
5. What does the snapshot ID bind?
6. Why can a live source state change while artifact integrity stays verified?
7. Why can moving an external revision break a report link?

## Summary

Corpus inspection aggregates existing evidence. It does not grant mutation
authority.

The static report is local and source-text-free. It connects grouped results to
their detailed records.

Verification checks the historical artifact. Optional live-input checks remain
advisory.
