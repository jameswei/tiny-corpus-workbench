# Interactive Document Lifecycle

Suggested time: 30–45 minutes.

## Learning goals

After this lesson, you can:

- complete one document lifecycle in the browser;
- connect a finding to a supported refiner;
- inspect a proposal without editing JSON;
- record an explicit approval or rejection;
- inspect immutable revision and reversal evidence;
- explain how browser proposal state differs from persisted evidence.

## Terms

A **finding** records a condition and cites document evidence.

A **proposal** describes one deterministic refinement before a decision.

A **decision** explicitly approves or rejects one proposal.

A **revision** is the immutable prepared document from an approved proposal.

## Before you start

Install the locked environment:

```bash
uv sync --frozen --python 3.12
```

Activate `.venv`:

```bash
source .venv/bin/activate
```

The guided example does not need Docling model files.

## Exercise

1. Create an isolated workspace.

   ```bash
   LESSON_WORKSPACE="$(mktemp -d /tmp/tcw-v08-lesson.XXXXXX)"
   printf '%s\n' "$LESSON_WORKSPACE"
   ```

2. Start the Workbench.

   ```bash
   corpus workbench --workspace "$LESSON_WORKSPACE" --no-open
   ```

3. Open the printed local address.

4. Select **Start whitespace lifecycle**.

5. Wait for the observation to complete.

   The Workbench verifies the workspace before it accepts the new record.

6. Inspect the observation details.

   The page identifies the observation as verified during admission.

7. Select **Diagnose document**.

8. Find the D009 whitespace finding.

   The page names the R001 whitespace normalization refiner.

9. Select **Create proposal**.

10. Compare each readable before and after value.

    Do not edit the proposal JSON.

11. Expand the CLI continuation details.

    The four paths support the unchanged `corpus resolve-refinement` command.

12. Select **Approve proposal**.

13. Inspect the approved refinement.

    Confirm its decision, transformation, revision chain, and reversal state.

14. Select **Diagnose prepared revision** if you want to continue.

15. Stop the Workbench with `Ctrl-C`.

## Decision experiment

Start the guided lifecycle again. Create its D009 proposal, then select
**Reject proposal**.

The rejection is an immutable refinement record. It has no prepared revision,
so the browser does not offer diagnosis continuation.

## Browser state and persisted evidence

A displayed proposal belongs to its diagnosis. You can select another record
while the proposal waits. Return to that diagnosis to see its proposal again
during the same page process.

A reload clears proposal panels. A server restart also clears the action token
and proposal context. Draft files and immutable records remain on disk. The
Workbench does not discover draft files as records.

Only `refinement-manifest.json.decision` is persisted decision authority. The
page, action token, proposal state, and transformation state are not authority.

## Check your understanding

1. Why does a diagnosis not authorize a document change?
2. What evidence appears only after approval?
3. Why can a rejected refinement not continue to diagnosis?
4. What happens to a proposal panel after a page reload?
5. Why is the local action token not authentication?

## Summary

The browser can observe, verify, diagnose, preview, and resolve one document
proposal without JSON editing.

Approval publishes one immutable revision with reversible evidence. Rejection
publishes the decision without a revision. The CLI remains available as an
optional continuation path.

Read the [Local Visual Workbench guide](../docs/local-visual-workbench.md) for
the complete current behavior and limits.
