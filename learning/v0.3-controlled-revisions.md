# Learn v0.3: Controlled Revisions

Estimated study time: 45 minutes.

## Learning goals

After this lesson, you can:

- explain why a finding does not approve a change
- inspect a proposal without editing it
- approve or reject with one explicit flag
- compare approved and rejected evidence
- verify a revision and its reversal

## Create a proposal

Observe and diagnose the whitespace fixture:

```bash
uv run corpus observe fixtures/refinement/whitespace-cleanup.md
uv run corpus diagnose OBSERVATION_DIRECTORY
```

Open `findings.json`. Copy the `finding_id` for `TCW-D009`. Then create a
proposal:

```bash
uv run corpus draft-refinement DIAGNOSIS_DIRECTORY \
  --finding FINDING_ID \
  --base OBSERVATION_DIRECTORY \
  --output whitespace-proposal.json
```

Open `whitespace-proposal.json` and inspect it. Do not edit the JSON. It records
proposal state `REQUESTED`, the diagnosis and base identities, the finding,
the refiner, exact forward and inverse edits, and `draft_id`.

The proposal descriptor is:

```text
path: proposal.json
role: refinement-proposal
media_type: application/json
```

## Approve the proposal

Use one explicit decision flag:

```bash
uv run corpus resolve-refinement whitespace-proposal.json \
  --diagnosis DIAGNOSIS_DIRECTORY \
  --base OBSERVATION_DIRECTORY \
  --approve
```

Verify the result:

```bash
uv run corpus verify-refinement REFINEMENT_DIRECTORY \
  --diagnosis DIAGNOSIS_DIRECTORY \
  --base OBSERVATION_DIRECTORY
```

Confirm that:

- `refinement-manifest.json.decision` is `APPROVED`
- `revision_id` is not null
- `transformation.json` has lifecycle state `APPLIED`
- derivation and reversibility are `MATCH`
- the record has proposal, report, transformation, history, and both prepared
  documents

The manifest decision is the only persisted structured decision authority.
The transformation state is not approval authority. `report.md` is a derived
human view, and the verifier checks its exact bytes.

## Reject a proposal

Create a new proposal for the same finding. Resolve it with `--reject`:

```bash
uv run corpus resolve-refinement whitespace-proposal-2.json \
  --diagnosis DIAGNOSIS_DIRECTORY \
  --base OBSERVATION_DIRECTORY \
  --reject
```

Confirm that:

- the command exits `0`
- the manifest decision is `REJECTED`
- `revision_id` and `parent` are null
- only `proposal.json` and `report.md` are listed artifacts
- no prepared directory, transformation, or history exists
- derivation and reversibility are `NOT_APPLICABLE`

Do not supply zero decision flags or both `--approve` and `--reject`. Both
forms are invalid before publication.

## Create a revision chain

1. Diagnose an approved refinement directory.
2. Select one supported finding from the new diagnosis.
3. Create a proposal with that refinement directory as `--base`.
4. Inspect the proposal without editing it.
5. Resolve it with `--approve`.
6. Open `history.json`.

Confirm that the child history contains the parent transformation first. The
new transformation is the history tail. Each transformation uses `draft_id`.

## Perform safe tamper experiments

Work only on copies.

1. Change whitespace or key order in a copied proposal before resolution.
2. Confirm that resolution fails and publishes nothing.
3. Copy a published refinement.
4. Change only `report.md`.
5. Confirm that verification exits `5`.

Repeat the publication test with a stale proposal and the verification test
with a changed transformation, history, or prepared document.

## Knowledge check

1. Does a diagnosis finding approve a change?
2. Which persisted JSON field is the decision authority?
3. Can you edit a proposal before resolution?
4. What does a rejected publication contain?
5. When can a refinement be a corpus revision?

## Expected answers

1. No. A person must supply an explicit resolution flag.
2. `refinement-manifest.json.decision`.
3. No. Resolution requires the exact canonical recomputed bytes.
4. A manifest plus `proposal.json` and the derived `report.md`.
5. Only after approval and full coherent verification.
